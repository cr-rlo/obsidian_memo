## 브라우저의 HTML과 CSS가 트리가 되는 과정
- 브라우저에 HTML 파일을 열면 즉시 화면이 표시되는 것처럼 보이지만, 실제로는 복잡한 내부 절차가 먼저 수행됨
- 첫 번째 핵심 절차는 문자열로 된 HTML과 CSS를 구조화된 객체 트리로 변환하는 과정
	- DOM과 CSSOM 생성
- HTML
	- 단순한 문자열에서 구조화된 데이터
	- 개발자에게는 구조가 있는 문서처럼 보이지만, 컴퓨터에게는 <,>, BODY 등으로 구성된 하나의 긴 문자열일 뿐임
	- 컴퓨터는 이 텍스트 만으로는 구조나 계층을 알 수 없음
	- 따라서 이 문자열을 해석하여 구조화된 데이터로 변환하는 전처리 작업을 수행함
	- 이 작업의 핵심 도구가 바로 파서
- 파서
	- 파서는 브라우저 내부에 내장된 프로그램으로, HTML이나 CSS 같은 텍스트를 해당 문법에 따라 분석하여 의미있는 조각들로 분해함
	- 이 조각들을 토큰이라고 부름
## HTML 파싱 과정
- 토큰 분해 예시
	- < h1 > Hello < /h1 >
	- 이 코드는 파서에 의해 세 개의 토큰으로 나뉨
	- 시작 태그 토큰
		- < h1 >
	- 텍스트 노드 토큰
		- Hello
	- 종료 태그 토큰 
		- < /h1 >
- 노드로 변환
	- 분해된 토큰들은 자바스크립트 객체인 노드로 변환됨
	- 각 노드는 type, tagName, children 같은 속성을 가짐
	- 전체 노드를 감싸는 최상위 구조로 document 노드
	- 이 노드들은 부모 자식간의 관계로 트리 계층 구조로 메모리에 연결되어 DOM 트리의 기본 단위를 이룸
## CSS 파싱
- CSS는 HTML의 시각적 표현을 담당하지만, 브라우저에겐 역시 단순한 텍스트일 뿐
- h1 { color: blue; }
	- 브라우저는 이 CSS 문자열을 분석하여 HTML과 유사하게 의미있는 작은 단위인 토큰으로 분해함
	- 선택자 토큰
		- h1
	- 시작 중괄호 토큰
		- {
	- 선언부 토큰
		- color: blue;
	- 종료 중괄호 토큰
		- }
- 이 분해된 토큰들은 브라우저가 인식할 수 있는 객체로 변환되고 계층적인 관계에 따라 최종적으로 CSSOM 트리를 형성함
- CSSOM
	- CSSOM은 스타일 정보를 담고 있는 메모리상의 구조화된 객체 트리로 자바스크립트를 통해 접근하고 조작할 수 있음
## CSSOM 파싱 로직: 규칙 추출 및 구조화
- 1. CSS 규칙 식별
	- 전체 CSS 텍스트에서 h1 { color: blue; }와 같이 한 줄짜리 완전한 CSS 규칙들을 정규 표현식 등을 활용하여 찾아냄
- 2. 선택자 및 선언부 분리
	- 식별된 각 규칙에서 선택자(h1)와 선언부( color: blue; )를 명확하게 분리함
- 3. 선언부 속성-값 분해
	- 분리된 선언부를 다시 color:blue;와 같이 개별 속상-값 쌍으로 쪼개어 객체 형태로 저장함
- 4. 구조화된 객체 변환
	- 이 과정을 통해 텍스트 형태의 CSS가 자바스크립트에서 쉽게 다룰 수 있는 구조화된 객체 형태로 변환됨
	- 이는 매우 기본적인 구문 분석기 역할을 수행함
## DOM과 CSSOM이 모두 필요한 이유
- CSSOM은 DOM과 평행적으로 생성되며 이 두 구조는 렌더링 과정에서 하나로 결합됨
- HTML안에 스타일 정보도 들어있는데 왜 굳이 CSSOM이라는 별도의 구조를 만들어야 할까?
- DOM은 웹 페이지에 어떤 요소들이 존재하는지, 즉 내용과 구조에 대한 정보를 제공함
	- 무엇을 그릴 것인가
- CSSOM은 각 요소가 어떤 모양, 색상, 위치를 가져야 하는지, 즉 시각적 표현에 대한 정보를 담당함
	- 그것을 어떻게 그릴 것인가
- 브라우저가 실제로 화면에 어떤 내용을 표시하려면, 이 두가지 정보가 반드시 필요하며, 상호 보완적인 역할을 수행함
## Render Tree: 보이는 것들의 구조
- Render Tree
	- 렌더 트리는 화면에 실제로 그릴 수 있는 요소들만을 대상으로, 계산된 스타일 정보를 포함한 시각화 전용 트리
	- DOM과 CSSOM의 조합
		- 단순히 둘을 합친 것이 아니라, 실제 화면에 표시되는 DOM 노드만 선별하고 각 노드에 스타일 정보를 매핑한 별도의 구조
		- 보이지 않는 요소 제외: display:none 속성이 적용도니 요소처럼 화면에 표시되지 않는 노드는 렌더 트리에서 제외됨
		- 스타일 정보 포함
			- 각 노드에는 색상, 폰트 크기, 정렬 방식 등 최종 계산된 스타일 정보가 담김
	- 시각적 요소만 포함
- DOM과 CSSOM, 이 두 가지 정보가 모두 준비되어야만 브라우저는 이들을 결합하여 최종적인 렌더링 구조인 Render Tree를 만들 수 있음
- Render Tree는 실제로 화면에 보이는 요소들만을 모아서, 각각에 어떤 스타일을 적용할지를 결정한 후, 최종적으로 화면에 배치하기 위한 내부 구조임
	- 브라우저 렌더링 엔진은 렌더 트리를 기반으로 레이아웃을 계산하고 화면에 픽셀을 그려 최종 화면을 완성함
- Render Tree를 만들기 위해서 CSS정보가 필수적이기 대문에 CSS파일이 외부에서 로딩 중일 때는 브라우저가 화면 렌더리을 멈추고 그 파일이 완전히 로드될 때까지 기다림
## 렌더링 흐름
- HTML 파싱
	- HTML 문서를 파싱하여 DOM 트리 생성
- CSS 파싱
	- CSS를 파싱하여 CSSOM 트리 생성
- 렌더 트리 구성 - 시각적 요소만 포함된 별도 구조
	- DOM + CSSOM(필터링+스타일 계산)
	- DOM트리의 각 노드를 순회함
	- 노드 태그 이름이 CSSOM의 선택자와 일치하는 규칙을 찾음
	- 일치하는 경우 해당 스타일 선언들을 노드에 매칭
	- 스타일이 적용된 새 객체를 만들어 렌더 트리에 추가
- 레이아웃
	- 렌더 트리 생성 후 화면에 그려지기 전의 핵심 단계
	- 위치와 크기 계산
	- 렌더 트리의 각 요소가 최종적으로 화면에 표시될 정확한 위치(x,y의 좌표)와 크기(너비, 높이)를 결정하는 과정
	
	- 렌더 트리의 각 노드를 순서대로 방문하며 시각적 속성 분석
	- 부모 요소의 속성과 css규칙에 따라 자식 요소의 절대적 위치와 크기 결정
	- 각 요소의 컨텐츠, 패딩, 보더, 마진을 포함한 최종 박스 모델 계산
	- 계산된 좌표와 크기 정보를 렌더 트리에 다시 반영하여 완벽한 시각화 트리 구성

	- 브라우저에서 레이아웃 계산은 매우 비용이 큰 작업 중 하나
		- 특히 돔 구조가 복잡하거나 레이아웃에 영향을 주는 변경이 자주 일어나는 경우 브라우저는 전체 또는 부분적인 레이아웃 재 계산을 수행해야 하며, 이를 리플로우 또는 레이아웃 스래싱이라고 함

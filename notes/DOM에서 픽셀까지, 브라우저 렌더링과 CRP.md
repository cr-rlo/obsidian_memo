## CRP
- 렌더링 흐름은 곧 성능 지연 지도
- 실무에서는 병목을 추적하고 해결하는 도구
- 성능 최적화 전략의 출발점
- Critical Rendering Path
	- 브라우저는 dom과 cssom을 합쳐 렌더트리를 만들고 이 트리를 바탕으로 레이아웃, 페인트, 컴포지트 단계를 거쳐 최종적으로 화면 출력
	- 이 전체적인 과정을 말함
## 브라우저의 HTML과 CSS가 트리가 되는 과정
- 브라우저에 HTML 파일을 열면 즉시 화면이 표시되는 것처럼 보이지만, 실제로는 복잡한 내부 절차가 먼저 수행됨
- 첫 번째 핵심 절차는 문자열로 된 HTML과 CSS를 구조화된 객체 트리로 변환하는 과정
	- DOM과 CSSOM 생성
- HTML
	- 단순한 문자열에서 구조화된 데이터
	- 개발자에게는 구조가 있는 문서처럼 보이지만, 컴퓨터에게는 <,>, BODY 등으로 구성된 하나의 긴 문자열일 뿐임
	- 컴퓨터는 이 텍스트 만으로는 구조나 계층을 알 수 없음
	- 따라서 이 문자열을 해석하여 구조화된 데이터로 변환하는 전처리 작업을 수행함
	- 이 작업의 핵심 도구가 바로 파서
- 파서
	- 파서는 브라우저 내부에 내장된 프로그램으로, HTML이나 CSS 같은 텍스트를 해당 문법에 따라 분석하여 의미있는 조각들로 분해함
	- 이 조각들을 토큰이라고 부름
## HTML 파싱 과정
- 토큰 분해 예시
	- < h1 > Hello < /h1 >
	- 이 코드는 파서에 의해 세 개의 토큰으로 나뉨
	- 시작 태그 토큰
		- < h1 >
	- 텍스트 노드 토큰
		- Hello
	- 종료 태그 토큰 
		- < /h1 >
- 노드로 변환
	- 분해된 토큰들은 자바스크립트 객체인 노드로 변환됨
	- 각 노드는 type, tagName, children 같은 속성을 가짐
	- 전체 노드를 감싸는 최상위 구조로 document 노드
	- 이 노드들은 부모 자식간의 관계로 트리 계층 구조로 메모리에 연결되어 DOM 트리의 기본 단위를 이룸
## CSS 파싱
- CSS는 HTML의 시각적 표현을 담당하지만, 브라우저에겐 역시 단순한 텍스트일 뿐
- h1 { color: blue; }
	- 브라우저는 이 CSS 문자열을 분석하여 HTML과 유사하게 의미있는 작은 단위인 토큰으로 분해함
	- 선택자 토큰
		- h1
	- 시작 중괄호 토큰
		- {
	- 선언부 토큰
		- color: blue;
	- 종료 중괄호 토큰
		- }
- 이 분해된 토큰들은 브라우저가 인식할 수 있는 객체로 변환되고 계층적인 관계에 따라 최종적으로 CSSOM 트리를 형성함
- CSSOM
	- CSSOM은 스타일 정보를 담고 있는 메모리상의 구조화된 객체 트리로 자바스크립트를 통해 접근하고 조작할 수 있음
## CSSOM 파싱 로직: 규칙 추출 및 구조화
- 1. CSS 규칙 식별
	- 전체 CSS 텍스트에서 h1 { color: blue; }와 같이 한 줄짜리 완전한 CSS 규칙들을 정규 표현식 등을 활용하여 찾아냄
- 2. 선택자 및 선언부 분리
	- 식별된 각 규칙에서 선택자(h1)와 선언부( color: blue; )를 명확하게 분리함
- 3. 선언부 속성-값 분해
	- 분리된 선언부를 다시 color:blue;와 같이 개별 속상-값 쌍으로 쪼개어 객체 형태로 저장함
- 4. 구조화된 객체 변환
	- 이 과정을 통해 텍스트 형태의 CSS가 자바스크립트에서 쉽게 다룰 수 있는 구조화된 객체 형태로 변환됨
	- 이는 매우 기본적인 구문 분석기 역할을 수행함
## DOM과 CSSOM이 모두 필요한 이유
- CSSOM은 DOM과 평행적으로 생성되며 이 두 구조는 렌더링 과정에서 하나로 결합됨
- HTML안에 스타일 정보도 들어있는데 왜 굳이 CSSOM이라는 별도의 구조를 만들어야 할까?
- DOM은 웹 페이지에 어떤 요소들이 존재하는지, 즉 내용과 구조에 대한 정보를 제공함
	- 무엇을 그릴 것인가
- CSSOM은 각 요소가 어떤 모양, 색상, 위치를 가져야 하는지, 즉 시각적 표현에 대한 정보를 담당함
	- 그것을 어떻게 그릴 것인가
- 브라우저가 실제로 화면에 어떤 내용을 표시하려면, 이 두가지 정보가 반드시 필요하며, 상호 보완적인 역할을 수행함
## Render Tree: 보이는 것들의 구조
- Render Tree
	- 렌더 트리는 화면에 실제로 그릴 수 있는 요소들만을 대상으로, 계산된 스타일 정보를 포함한 시각화 전용 트리
	- DOM과 CSSOM의 조합
		- 단순히 둘을 합친 것이 아니라, 실제 화면에 표시되는 DOM 노드만 선별하고 각 노드에 스타일 정보를 매핑한 별도의 구조
		- 보이지 않는 요소 제외: display:none 속성이 적용도니 요소처럼 화면에 표시되지 않는 노드는 렌더 트리에서 제외됨
		- 스타일 정보 포함
			- 각 노드에는 색상, 폰트 크기, 정렬 방식 등 최종 계산된 스타일 정보가 담김
	- 시각적 요소만 포함
- DOM과 CSSOM, 이 두 가지 정보가 모두 준비되어야만 브라우저는 이들을 결합하여 최종적인 렌더링 구조인 Render Tree를 만들 수 있음
- Render Tree는 실제로 화면에 보이는 요소들만을 모아서, 각각에 어떤 스타일을 적용할지를 결정한 후, 최종적으로 화면에 배치하기 위한 내부 구조임
	- 브라우저 렌더링 엔진은 렌더 트리를 기반으로 레이아웃을 계산하고 화면에 픽셀을 그려 최종 화면을 완성함
- Render Tree를 만들기 위해서 CSS정보가 필수적이기 대문에 CSS파일이 외부에서 로딩 중일 때는 브라우저가 화면 렌더리을 멈추고 그 파일이 완전히 로드될 때까지 기다림
## 렌더링 흐름
- HTML 파싱
	- HTML 문서를 파싱하여 DOM 트리 생성
- CSS 파싱
	- CSS를 파싱하여 CSSOM 트리 생성
- 렌더 트리 구성 - 시각적 요소만 포함된 별도 구조
	- DOM + CSSOM(필터링+스타일 계산)
	- DOM트리의 각 노드를 순회함
	- 노드 태그 이름이 CSSOM의 선택자와 일치하는 규칙을 찾음
	- 일치하는 경우 해당 스타일 선언들을 노드에 매칭
	- 스타일이 적용된 새 객체를 만들어 렌더 트리에 추가
- 레이아웃
	- 렌더 트리 생성 후 화면에 그려지기 전의 핵심 단계
	- 위치와 크기 계산
	- 렌더 트리의 각 요소가 최종적으로 화면에 표시될 정확한 위치(x,y의 좌표)와 크기(너비, 높이)를 결정하는 과정
	
	- 렌더 트리의 각 노드를 순서대로 방문하며 시각적 속성 분석
	- 부모 요소의 속성과 css규칙에 따라 자식 요소의 절대적 위치와 크기 결정
	- 각 요소의 컨텐츠, 패딩, 보더, 마진을 포함한 최종 박스 모델 계산
	- 계산된 좌표와 크기 정보를 렌더 트리에 다시 반영하여 완벽한 시각화 트리 구성

	- 브라우저에서 레이아웃 계산은 매우 비용이 큰 작업 중 하나
		- 특히 돔 구조가 복잡하거나 레이아웃에 영향을 주는 변경이 자주 일어나는 경우 브라우저는 전체 또는 부분적인 레이아웃 재 계산을 수행해야 하며, 이를 리플로우 또는 레이아웃 스래싱이라고 함
- 페인트
	- 픽셀 그리기
	- 렌더링 파이프라인의 시각적 완성
	- 레이아웃 단계에서 각 요소의 위치와 크기가 확정되면 브라우저는 이제 페인트 단계를 통해 실제 화면에 픽셀을 채색함
	- 요소의 위치와 스타일이 정해진 이후, 브라우저가 이 정보를 토대로 실제 픽세 ㄹ단위로 색상을 채우는 작업임
	- 배경 및 색상 채우기
	- 텍스트 및 그래픽 그리기
	- 테두리 및 효과 적용
- 렌더링 속성 유형
	- 스타일 요소의 사소한 부분이 변화해도 브라우저가 매 프레임마다 해당 요소를 다시 칠해야 하므로 성능 저하 우려
	- 이러한 성능 저하 문제를 방지하기 위해서 CSS 속성들이 렌더링 파이프 라인에 미치는 영향에 따라 세 가지 주요 범위로 분류
	- paint-only 속성
		- 레이아웃에는 영향을 주지 않고 페인트만 재실행하는 속성
		- GPU자원을 사용하지만, 레이아웃 재계산 비용은 발생하지 않음
		- color
		- background-color
		- box-shadow
	- composite-only 속성
		- 레이아웃도 페인트도 다시 하지 항ㄴ고
		- GPU 계층에서 합성만 다시하는 최적화된 속성
		- 가장 성능비용이 낮음
		- transform
		- opacity
		- transform: translateX()
	- layout-affecting 속성
		- DOM요소의 크기나 위치에 영향을 주어 레이아웃과 페인트를 모두 재실행시키는 속성
		- 가장 비용이 큰 작업
		- width, height
		- padding, margin
		- display, position
- composite-only 속성을 우선적으로 활용하는 전략을 사용하는 것이 좋음
- 컴포지팅 단계
	- 최종 화면 합성과 GPU 가속
		- 스크롤, 애니매이션 등 동적으로 움직이는 요소들을 별도 레이어로 분리하면 GPU가 이들을 독립적으로 효율적으로 처리할 수 있어 부드러운 사용자 경험을 제공
	- 여러 레이어를 하나로 합쳐 최종적인 이미지를 만들고, 이를 화면에 표시하는 과정
	- 복잡한 픽셀 연산이 필요한 페인트와 달리 컴포지팅은 주로 GPU가속을 활용하여 효율적으로 처리됨
	- 쉽게 말해 화면의 각 조각들을 하나로 합쳐 하나의 그림처럼 만드는 최종 작업
	- 브라우저는 렌더링 성능을 극대화하기 위해 화면에 표시할 요소들을 상황에 따라 여러 개의 레이어로 나누어 처리
		- 각 요소를 독립적인 레이어로 분리함으로써 특정 요소가 변경될 때 전체 화면을 다시 그릴 필요없이 해당 레이어만 업데이트하여 렌더링 비용을 줄임
	- 포토샵이나 피그마 같은 디자인 툴에서 여러 레이어를 겹쳐 하나의 이미지를 만드는 것과 유사한 개념

# 브라우저 devTools를 통한 렌더링 구조 분석
## Elements & computed 
- 크롬 개발자 도구 사용
- elements
	- 브라우저 내부의 DOM 구조를 실시간 확인
	- 로드된 HTML의 DOM구조가 트리형태로 표시
	- 단순 HTML 텍스트가 아니라 브라우저가 메모리에 구성한 DOM 객체 트리의 시각적 표현
- computed
	- 각 요소의 최종 CSSOM 계산 결과를 시각적으로 확인
	- 브라우저가 계산한 최종 스타일 값 확인 가능
	- 이 값은 여러 CSS 소스, 상속, 기본값을 모두 반영
	- 요소가 최종적으로 어떤 스타일을 갖는지 확정된 결과를 보여줌
- 두 탭은 가장 기본적이고 중요한 도구
- DOM/ CSSOM이 실제 브라우저에서 어떻게 표현, 연결되는지 확인하기 위해 반드시 이해해야 함
## performance 타임라인
- 브라우저의 렌더링 작업 순서와 실행 시점을 추적할 수 있는 도구
- Recalculate Style, Layout, Paint, Composite 순서를 실제로 확인 가능
- 단순 이론을 넘어 렌더링 실행 타이밍 , 순서, 병목 구간까지 분석 가능
## 레이아웃 시프트와 CLS
- 일상에서 웹 페이지의 화면이 흔들린다고 표현하는 이 현상은 개발자나 브라우저의 관점에서는 레이아웃 시프트라고 부름
- 웹페이지 안의 요소들이 사용자 상호작용 없이 예기치 않게 시각적으로 이동하는 것을 의미
- 사용자가 아무런 행동도 하지 않았는데 버튼, 텍스트, 이미지 같은 요소가 갑자기 위 아래 옆으로 밀려남 -> 이는 사용자 경험 저해, 의도치 않은 클릭 유발 가능
- CLS(cumulative layout shift)
	- 웹페이지에서 발생하는 모든 예기치 않은 위치 변화의 크기를 합산한 값
	- 측정 기준
		- 0.1이하: 안정적인 사이트로 간주
		- 0.25이상: 개선이 시급한 사이트
	- 중요성
		- 이 수치가 검색 결과 순위에 직접적인 영향을 미칠 수 있음

- 페인트 플래싱
	- 성능 문제의 시각적 신호
	- 브라우저가 화면의 요소를 다시 그릴 때마다 해당 요소의 테두리에 초록색 선을 반짝여 표시함
	- 특정 요소가 계속해서 초록색으로 반짝인다면 해당 요소가 지속적으로 리페인트되고 있음을 시각적으로 알려주는 신호
	- 이는 곧 해당 요소가 브라우저 성능에 부담을 주고 있으며 최적화가 필요하다는 것을 의미
## FPS: 애니매이션 성능 분석
- 스크롤이 끊기거나 애니매이션이 부자연스러움 -> 브라우저가 화면을 충분히 빠르게 그리지 못하고 있음
- FPS가 높을수록 부드러운 화면 전환
- FPS가 낮아지면 버벅임, 끊김
- FPS는 브라우저가 1초에 화면을 몇 번 업데이트 하는지 나타냄
- 60FPS
	- 초당 60장의 화면을 보여줄 때 가장 자연스럽고 부드러운 움직임을 제공
	- 웹 애니메이션과 사용자 인터랙션의 목표 기준
- 30FPS 이하: 끊김 발생
	- 프레임 수가 30 FPS 이하로 떨어지면 화면의 끊김이 눈에 띄게 감지되기 시작
- 15FPS 이하
	- 거의 슬라이드 쇼를 보는 것 처럼 심하게 버벅임

## DOMContentLoaded-load-beforeunload-unload
- DOMContentLoaded 이벤트
	- DOMContentLoaded이벤트는 HTML문서가 완전히 로드되고 파싱되어 DOM트리가 성공적으로 완성되었을 때 발생
	- 이 시점부터 개발자는 안전하게 이벤트 리스너를 등록하고 요소를 선택하며 내용을 조작할 수 있음
	- HTML 파싱이 완료되었을 뿐 이미지, CSS, 폰트같은 외부 리소스는 아직 로드 중일 수 있음
		- 브라우저는 script 태그를 발견하면 HTML 파싱을 일시 중지하고 스크립트 로드 및 실행을 시작
		- 모든 자바스크립트 코드가 파싱되고 나면 브라우저는 중단했던 HTML 파싱을 재개함
		- HTML 파싱이 완전히 끝나고 모든 DOM 노드가 생성된 시점에 DOMContentLoaded 이벤ㅌ가 발생
	- 브라우저가 body 태그를 닫기 전까지 모든 HTML 요소를 메모리에 객체로 올려놓았다는 신호
- load 이벤트
	- DOMContentLoaded보다 한 단계 뒤에서 발생
	- DOM뿐만 아니라 이미지, CSS 파일, 자바스크립트 파일, iframe등 모든 외부 자원까지 전부 로딩이 완료된 이후에 발생
	- load는 브라우저가 페이지 전체를 완전히 로딩했다는 종합적인 신호
	- 배너 이미지의 사이즈를 기반으로 레이아웃을 계산해야 하거나 모든 스타일 파일이 적용된 이후에 UI를 구성해야할 때 적절
	- 특히 복잡한 이미지나 광고를 포함한 페이지에서는 load 이벤트 발생이 지연되어 사용자 경험에 부정적인 영향을 미칠 수 있음
	- 따라서 DOM 조작만 필요한 경우에는 DOMContentLoaded가 훨씬 빠르고 대체로 권장됨
- beforeunload 이벤트
	- 사용자가 현재 페이지를 떠나려고 시도할 때 발생
	- 브라우저 탭을 닫거나 다른 URL로 이동하거나 페이지를 새로 고침하는 등의 사용자 행동으로 트리거될 수 있음
	- 개발자가 사용자에게 마지막 확인 기회를 제공할 수 있는 중요한 시점
	- 정말 나가겠습니까? 와 같은 시스템 경고 메세지를 띄워 마지막으로 행동을 되돌릴 기회를 제공
- unload 이벤트
	- 페이지가 실제로 닫히는 순간 발생
	- 브라우저가 다른 페이지로 이동하거나 탭이 종료될 때 트리거
	- 브라우저가 네트워크 요청 완료를 기다리지 않고 강제로 탭을 종료할 수 있어 unload 이벤트 내부에서 중요한 작업이 보장되지 않음
	- 사용자가 페이지를 떠나는 즉시 브라우저는 리소스 해제를 시작하므로 unload이벤트 핸들러가 실행될 충분한 시간을 확보하기 어려움
	- 이러한 이유로 과거에는 로그전송이나 쿠키 정리 등에 unload 이벤트가 사용되었으나, 이제는 중요하지 않은 작업에만 사용하거나 sendBeacon( )과 같은 더 현대적이고 신뢰할 수 있는 대안 고려
- sendBeacon( )
	- sendBeacon API는 웹 페이지가 닫히는 순간에도 백그라운드에서 서버로 데이터를 안정적으로 전송할 수 있도록 설계된 비동기 네트워크 API
	- 기존의 fetch나 XMLHttpReauest와 달리 페이지가 언로드 되더라도 요청이 중단되지 않고 병렬적으로 전송되어 데이터 손실을 최소화
## 렌더링 차단 자원 - CSS, JS 최적화 기법
- 브라우저가 웹페이지를 화면에 그리는 과정에서 가장 큰 영향을 미치는 요소 중 하나는 바로 렌더링을 지연시키는 리소스
- CSS와 자바스크립트 파일은 브라우저의 렌더링 파이프라인을 직접적으로 차단하여 화면 출력 속도를 늦출 수 있음
	- CSS는 head태그에 포함시키는 것이 바람직함
- link rel = "preload" href="" as= "image"
	- 반드시 head 내부에 배치
	- 속성: as로 자원타입 명시 -> 브라우저 우선 순위를 올바르게 판단
	- 효과: CSSOM, RenderTree 생성에 필요한 자원을 미리 확보
	- 이미지, 주요 웹 폰트, 초기 실행 JS 등
	- FCP, LCP 개선 등 핵심 웹 성능 지표 향상
- link rel = "prefetch" href=""
	- 곧 필요해질 수 있는 리소스를 미리 다운
	- 현재 렌더링에는 영향 없음
	- 다음 페이지 전환 대비 JS, CSS, 이미지 사전 로드
	- head에 선언 권장 -> speculative parser가 즉시 감지 가능
- link rel = "preconnect" href="" crossorigin
	- preconnect -> 외부 서버와 DNS조회, TCP 연결, TLS 핸드셰이크를 미리 수행
	- 외부 API, CDN, 폰트 서버와의 연결 예상 시 선언
	- head에 배치해 브라우저가 최대한 빨리 연결 준비
- defer
	- HTML 파싱과 스크립트를 병렬 다운로드, 파싱 완료 후 실행, 실행 순서 보장
- async
	- 다운로드 완료 즉시 실행, 실행순서 불보장 -> 독립적 스크립트에 적합
- 즉, CSS는 헤더에, 스크립트는 defer속성을 활용해 비동기적으로 로딩
- Speculative Parsing을 활용하여 브라우저가 리소스를 미리 예측하고 다운로드 하도록 하여 페이지 로딩 속도를 향상시키는 기능을 최대한 활용
- 리소스 힌트 적극 사용
## Speculative Parsing과 prelaod/async/defer
- 병렬로딩 전략
- 웹페이지 요청 시 브라우저 HTML을 위에서 아래로 한 줄씩 읽으며 DOM트리를 구성
- 이 과정에서 script같은 외부 스크립트 파일을 만나면, 브라우저 HTML 파싱을 잠시 멈춤
- 하지만 이런 방식은 전체 로딩을 지연시킬 수 있기 때문에 브라우저는 Speculative Parsing 방식을 도입
- 백그라운드 HTML 스캔
	- 브라우저는 스크립트 실행 때문에 메인 HTML 파싱이 멈추더라도, 백그라운드에서 HTML 토큰을 계속 스캔
	- 이 과정에서 외부 스크립트, 스타일시트, 이미지 등의 리소스를 메인 파싱과 병렬로 미리 다운로드
	- 브라우저는 실제 DOM트리를 구성하지 않고 토큰 단위로 필요한 리소스를 선제적으로 수집
	- 이렇게 준비된 리소스는 파싱이 재개될 때 즉시 활용될 수 있으며, 불필요한 경우 무시되거나 다시 처리될 수 있음
	- 결과적으로 리소스 로딩이 병렬로 이루어져, 전체 로드 성능이 크게 향상됨
- script src="" async
	- script에 async 속성을 붙인다면
	- HTML 다운로드와 script 다운로드가 병렬로 진행
	- 다운로드가 끝나는 즉시 실행되므로 실행 순간에는 파싱이 잠시 멈춤
	- script 태그 위치와 상관없이 병렬 다운로드가 가능해 일반 스크립트 태그 보다 빠름
	- 여러 개의 async 스크립트가 있을 경우 실행 순서는 보장되지 않음
	- 광고, 트래킨 소스, 소셜 버튼 등 다른 코드와 의존성이 없는 외부 스크립트에 적합
- script src"" defer
	- defer 스크립트는 HTML 파싱과 동시에 다운로드
	- DOM 파싱이 완료된 직후, DOMContentLoaded 이벤트 직전에 실행됨
	- 여러 개의 defer 스크립트가 있을 경우 작성된 순서대로 실행됨
	- HTML 파싱을 차단하지 않아 초기 렌더링 속도를 높이고 안정성과 성능을 모두 확보할 수 있음
	- DOM 조작이 필요한 주요 스크립트, 의존성이 있는 앱 초기화 코드 등에 가장 추천되는 방식
- link rel="preload" as="script" href="예시"
- script scr="예시"
	- preload가 먼저 선언되면 브라우저는 script를 즉시 다운 시작
	- script src를 만나면 이미 준비된 파일을 바로 실행
	- 대용량 스크립트, 웹폰트 등 늦게 쓰이지만 중요한 리소스에 적합
	- 미리 다운로드 하여 실행 시 대기 시간 최소화
	- 로딩 속도 개선 -> 사용자 체감 성능 향상
## Lazy loading의 중요성
- 웹페이지를 처음 열었을 때 화면 아래쪽에 있는 이미지나 글꼴까지 모두 한꺼번에 불러올 필요는 없음
- 사용자가 아직 보지도 않은 요소까지 미리 로딩하면 초기 페이지 로딩 속도가 느려지고 사용자의 데이터도 불필요하게 낭비됨
- 레이지 로딩은 지금 필요하지 않은 요소는 나중에 불러오는 방식
- img src="" loading="lazy
	- 브라우저가 이미지를 뷰포트에 들어오기 직전가지 로딩을 지연
	- 초기 페이지 로딩 속도를 개선하고 불필요한 네트워크 사용을 줄임
	- 뷰포트
		- 사용자가 실제로 보고있는 브라우저 화면의 가시 영역
		- 스크롤 할 때마다 이 영역이 바뀌며 lazy load믄 이 영역 근처에 다가올 때 리소스를 가져옴
- @font-face
	- @font-face{ font-family: css에서 사용할 이름(별칭);
	- src: url
	- format(): 브라우저가 이해할 수 있는 폰트 파일 형식
	- font-display: swap 폰트 다운로드 전까지 시스템 폰트를 먼저 보여주고 다운로드 완료 시 교체 유도}
- 웹폰트 preload 시 주의할 점
	- CORS 정책 때문에 반드시 crossorigin 속성을 지정해야 함
	- crossorigin은 브라우저가 외부 출처 자원을 가져올 때 인증, 접근 제어방식으 ㄹ정의
	- 구글 폰트나 CDN 폰트 사용시는 crossorigin="anonymous"가 있어야 함
## intersection observer
- 예전에는 DOM 요소가 화면에 들어왔는지 감지하기 위해 scroll 이벤트+getBoundingClientRect( )조합을 사용
	- 스크롤 이벤트가 발생할 때마다 DOM요소의 위치를 계산하여 뷰포트 안에 있는지 여부를 확인
	- 조건이 맞으면 이미지 로딩같은 동작을 수동으로 실행하는 방식
	- 이 방식은 동작 자체는 정확하나 사용자가 스크롤 할 때마다 이벤트가 지속적 발생
	- 매번 모든 대상 요소의 위치를 계산해야 하므로 연산 비용이 큼
	- 결과적으로 페이지가 느려지거나 프레임이 끊기는 문제 유발
- getBoundingClientRect( )
	- 이 메서드는 DOM요소의 위치와 크기를 브라우저 뷰포트 기준 좌표값으로 반환
	- 반환되는 객체에는 { top, left, bottom, right, width, height }같은 정보가 포함
	- 좌표는 브라우저 창의 왼쪽 모서리 (0,0)을 기준으로 계산됨
	- 이 값을 활용하면 요소가 현재 화면 안에 있는지, 아니면 밖에 있는지를 정확히 판별
- intersection Observer API
	- 위 문제 해결
	- 이 요소가 화면에 들어오면 나한테 알려줘 라는 방식
	- 브라우저에 등록만 해두면 브라우저가 알아서 체크하고 알려주는 구조
	- 따로 계산하거나 반복해서 확인할 필요가 없음
	- .isIntersecting
		- 픽셀이 한줄이라도 보이면 true값
		- 요소가 완전히 화면을 벗어나면 false값 반환

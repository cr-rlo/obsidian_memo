## 자바스크립트 엔진
- 인간 친화적인 고수준 언어에 속하는 자바스크립트 코드를 인터프리터나 컴파일 과정을 거쳐 컴퓨터의 cpu가 이해할 수 있게 하는 작업이 필요함
- 이 작업을 엔진이라고 함
- 고수준 언어
	-  추상화 수준이 높음
	- 가독성이 높고 유지보수가 용이함
	- 사람이 이해하기 쉬운 언어
- 저수준 언어
	- 기계가 이해하기 쉬운 언어
	- 실행속도가 빠르고 성능이 좋음
	- 가독성이 낮고 유지보수가 어려움
- JIT 컴파일러
	- 프로그램 실행 시점에 기계어로 번역하는 컴파일 기법
	- 동적 컴파일러
	- 인터프리터와 컴파일러의 혼합 방식
- 인터프리터
	- 프로그래밍 언어의 소스코드를 바로 실행하는 컴퓨터 프로그램
	- 파이썬, 자바스크립트, 루비 등
	- 소스 코드를 한 줄씩 읽어들여 실행
		- 이로 인해 컴파일 하는 과정이 없기 때문에 시간 비용을 아껴 실행 시간이 빠름
	- 정적 컴파일처럼 실행 파일을 별도로 생성하지 않고 실행시마다 인터프리트 과정이 반복 실행되어 실행 속도가 느림
	- 자바스크립트는 컴파일이 정적 컴파일러처럼 프로그램 실행 전 미리 처리되는 것이 아니라 런 타임에 처리되는 특성 때문에 인터프리터 언어로 구별되고 있지만 정확한 분류가 어려워 이 둘 간의 기술적 구분이 점점 사라지고 있음
- 컴파일러
	- 고수준언어로 작성된 소스코드를 저수준 언어로 번역해주는 프로그램
	- c, c++, c#, java 등
	- 한 줄씩 코드를 읽으며 실행하는 인터프리터와 다르게 정적 컴파일러는 실행 전 전체 소스코드를 한번에 기계언어로 번역 후 실행파일을 만듦
	- 컴파일 단계와 실행 단계가 분리되어 있으며 컴파일은 단 한 번만 수행
	- 단, 프로그램의 규모가 크거나 복잡한 경우 컴파일 시간이 오래걸려 실행시간이 느리다는 단점이 있음
	- 실행 시에는 또 다시 컴파일 과정을 거치지 않고 앞서 만들어진 실행 파일을 실행만 하면 되기 때문에 코드 실행 속도는 인터프리터에 비해 훨씬 빠름
- JIT VS 인터프리터 VS 컴파일러
	- JIT가 정적 컴파일러나 인터프리터보다 무조건 좋을까?
		- 실행 성능으로는 정적 컴파일러가 가장 좋음
		- JIT와 인터프리터는 동적 환경에서 실행된다는 공통점
			- 코드를 한 줄씩 읽는다는 것도 비슷
			- 그러나 JIT는 런타임 중에 최적화가 필요한 코드르 수집해 컴파일 과정을 거치기 때문에 인터프리터보다는 JIT가 빠름

## V8 엔진의 동작방식
- 1. 자바스크립트 소스에서 파서로 코드를 보냄
	- 파서는 전달받은 자바스크립트 코드를 어휘분석(Lexical Analysis)을 통해 코드를 토큰으로 분해함
		- 키워드, 식별자, 연산자/구분자로 토큰이 분해됨
	- 파서는 앞서 만든 토큰을 구문 분석(Syntax analysis) 과정을 진행함
		- 이 때 문법 에러가 있다면 syntax error이라는 메세지 출력
	- 문법 에러가 없다면 필요한 필요한 정보들만 추려서 트리 형태로 만듦
		- 이 트리가 바로 AST라고 부르는 Abstract Syntax Tree임
- 2. 이 추상구문트리 AST를 Ignition 이라는 곳에 전달
	- 이그니션이란 바이트 코드를 생성하는 V8의 빠른 인터프리터
		- 바이트 코드란 기계어를 추상화 한 코드
		- 즉, 고수준 언어인 자바스크립트 소스 코드를 가상 머신이 한결 편하게 이해할 수 잇도록 IR이라고 부르는 중간 언어로 번역한 것을 의미함
- 3. 이그니션은 바이트 코드를 실행하면서 프로파일링 및 피드백 데이터 수집
	- 이러한 데이터들은 TurboFan 컴파일러에서 최적화 기계어 코드를 생성하는 데 사용됨
		- 이그니션은 바이트 코드를 실행하면서 수집한 정보들을 바탕으로 코드가 Hot(반복되어 사용되는지), 코드의 양과 여러 복잡한 조건에 따라 sparkPlug가 컴파일 할지 TurboFan이 컴파일 할지 결정됨
	- SparkPlug
		- 스파크플러그란 이그니션과 터보팬 사이에 위치한 비최적화 컴파일러 
		- 스파크플러그는 빠르게 컴파일되도록 설계되었는데 그것이 가능한 이유 중 하나로는 parser가 생성한 AST기반이 아니라 이그니션이 생성한 바이트 코드를 기반으로 기계어를 만들어내기 때문
	- TurboFan
		- 스파크플러그와 마찬가지로 AST가 아닌 이그니션이 만든 바이트 코드를 기반으로 하며 이그니션이 실행하며 수집한 프로파일링과 피드백 데이터들을 이용하여 복잡하고 정교하게 최적화하여 기계어 코드로 변환하는 V8의 최적화 컴파일러임
		- 터보팬이 사용하는 최적화 기법에는 히든 클래스, 인라인 캐싱 등이 있음
		- 최적화했던 코드가 더 이상 최적화하기에 적합하지 않다고 판단되면 해당 코드를 다시 원래의 코드로 되돌리는 역 최적화를 진행
			- 이러한 불필요한 행위 때문에 성능에 영향을 끼칠 수도 있음
## 인라이닝
- 인라이닝은 자주 호출되는 작은 함수에 효과적
- 함수 호출은 반환 주소 및 여러 상태들을 스택에 push하고 함수 코드 위치로 점프하는 등 일련의 과정들을 가지고 있음
	- 인라이닝을 하는 것은 이 과정들을 생략하고 비용을 아낄 수 있기 때문에 최적화가 가능하다고 할 수 있음
	- 그러나 현대에 들어서는 브라우저와 하드웨어의 성능이 워낙 좋아졌기 때문에 이 인라이닝 최적화만으로 성능 개선에 큰 도움이 된다고 보기는 어려움
- 개발자의 관점에서 이전에 본 함수가 여러 파일들과 여러 함스로 나눠져 있다고 생각해보자
	- 만약 이름만 보고 무슨 일을 하는지 모르는 함수들이 여러 파일로 분리되어 있을 경우 개발자는 파일을 하나씩 들여다보고 분석하는 과정을 거쳐야 함
	- 여러 함수로 나눠져있는 코드보다는 하나로 합쳐진 함수를 대상으로 최적화하는 것이 훨씬 쉬움
	- 따라서 인라이닝 최적화는 엔진이 다른 최적화 작업들을 조금 더 쉽게 할 수 있도록 도와준다는 이점도 있음
# V8 엔진의 최적화 전략 히든클래스
- 히든 클래스
	- v8뿐만 아니라 다른 자바스크립트 엔진들도 최적화에 사용함
	- v8에서는 maps, 자바스크립트코어에서는 structures, 스파이더 몽키에서는 shapes라고 부르고 있음
## 자바스크립트 객체 모델과 속성 접근 방식
- 자바스크립트를 사용하여 개발시 object에 설정한 데이터를 이용하기 위해 object 내에 속성들에 접근하는 행위들을 많이 함
- ECMAScript의 스펙을 살펴보면 자바스크립트 오브젝트를 사전 형태로 정의하고 있는 것을 알 수 있음
## 히든 클래스 기본구조
- 예를 들어 name, height, weight 속성을 가지는 object가 있다고 가정하자
- 이 때 v8은 히든클래스를 사용하여 object를 다음과 같이 나타냄
	- name => offset: 0 / writable : True / enumerable: True / configurable:True 
	- height => offset: 1 / writable : True / enumerable: True / configurable:True 
	- width => offset: 2 / writable : True / enumerable: True / configurable:True 
- 이 상황에서 동일한 속성을 가진 human 2, 3라는 객체를 생성했다고 가정
- 기존대로라면 각 객체마다 property atrribute를 중복해서 가지고 있었을 테지만 이 오브젝트들은 모두 정확히 같은 히든 클래스를 공유하게 됨
- 즉 동일한 구조를 가지는 오브젝트가 얼마나 생성되든 간에 히든 클래스와 프로퍼티 정보를 단 한번만 저장하면 되고 오브젝트의 프로퍼티에 접근할 때 동적 탐색을 피하며 이미 생성된 히든클래스를 재사용할 수 있다는 이점이 있음
- 동일한 구조를 가지는 오브젝트면 동일한 히든 클래스를 가진다고 했는데 human2라는 빈 객체를 먼저 생성하고 동적으로 값을 할당한다면?
	- 최종 오브젝트의 형태는 위와 같겠지만 히든 클래스는 서로 다르게 갖게 됨
## Transition chains
- const human = { };
	- human 변수에 빈 오브젝트를 할당하면 오브젝트는 빈 히든 클래스를 갖게 됨
	- hidden class: empty => 이 히든 클래스를 c0라고 지칭하겠음
- 다음으로 human.name = '이름' 에 동적 할당하는 코드를 실행하게 되면 name 프로퍼티에 값을 할당하면서 새로운 히든 클래스인 c1이 생성되고 name 프로퍼티에 대한 offset을 가지게 됨
- 그리고 c0을 가리키던 오브젝트는 c1히든 클래스를 가리키게 되며 이때 c0에서 c1으로 전환되었다는 정보가 트랜지션으로 c0히든클래스에 저장됨
- 다음으로 height 프로퍼티에 값을 할당하면서 새로운 히든 클래스인 c2가 생성되고 height 프로퍼티에 대한 offset값을 가지게 됨
- c1을 가리키던 오브젝트는 역시 c2를 바라보게 되고 마찬가지로 c1에서 c2로 전환된다는 정보가 트랜지션이란 속성으로 c1히든 클래스에 저장됨
- weight에 정보를 할당하는 과정도 마찬가지
- 각 히든 클래스들은 transition이라는 정보 뿐만 아니라 back pointer라는 이전 클래스에 대한 참조 정보도 들고 있기 때문에 서로 체인 형태로 연결
- 따라서 c2의 경우 name 프로퍼티를 c1 히든 클래스에서 찾을 수 있기 때문에 가지고 있을 필요없이 height만 들고 있으면 되며 다른 것도 마찬가지
- 히든 클래스가 모두 연결되어 트랜지션 체인 구조가 완성
## 인라인 캐싱 동작 방식
- 코드를 실행하면 히든 클래스를 먼저 조회한 후 프로퍼티의 offset및 그외의 속성들을 가짐
- 반복해서 호출되며 특정 조건을 만족하는 패턴을 발견하는 경우 엔진은 바이트 코드를 실행 후 인라인 캐싱 정보를 포함한 슬롯을 저장하게 됨
- 이 슬롯에는 인라인 캐싱상태와 반복해서 접근한 객체의 히든 클래스 주소 및 접근한 속성에 대한 offset등이 들어있음
- 인라인 캐싱을 사용하면 객체 속성에 접근 시 캐싱되어 있는 히든 클래스와 우리가 접근하려고 하는 객체의 히든 클래스를 비교하여 동일한 경우 프로퍼티 정보를 더 이상 조회할 필요 없이 캐싱된 offset을 이용하여 바로 value값을 바로 가져올 수 있음
- 
## 인라인 캐싱 상태 (Transition state)
- UNINITIALIZED(0)
	- 아직 속성에 대한 접근이 실행되지 않은 상태
	- 
- PREMONOMORPHIC(.)
	- 해당 코드상엔 실제로 존재하지는 않지만 해당 파일의 주석을 살펴보면 개념으로만 존재하고 있는 값으로 속성에 대한 접근이 한 번 실행되었으며 다음 실행에선 MONOMORPHIC으로 전환될 가능성이 높은 상태
- MONOMORPHIC(1)
	- 속성 접근이 항상 같은 히든 클래스로 실행되었다는 뜻
	- 히든 클래스가 같은 객체를 반복해서 접근하는 경우 
- POLYMORPHIC(P)
	- 속성 접근이 2~4개 사이에 다른 히든 클래스로 실행되는 경우 캐싱되는 상태
	- 
- MEGAMORPHIC(N)
	- 5개 이상의 히든 클래스로 속성에 접근하면 이 상태로 캐싱 상태가 전환
	- 속도가 가장 느림

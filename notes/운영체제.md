- 컴퓨터는 기본적으로 운영체제 없이도 작동하지만, 운영체제가 없으면 처음 설계한 그대로만 동작할 뿐 다른 기능을 추가할 수 없음 -> 유연하지 못함
- 운영체제가 하는 일
	- 프로세스 관리
	- 메모리 관리
	- 하드웨어 관리
	- 파일 시스템 관리

## 운영 체제의 구조
- 커널
	- 프로세서와 메모리, 저장 장치를 관리하는 핵심적인 기능 담당
	- 사용자는 운영체제의 커널에 직접 접근할 수 없고 인터페이스를 통해서 접근
	- 어플리케이션은 시스템콜(인터페이스)을 통해 커널에 접근할 수 있음
	- 시스템콜 없이 어플리케이션이 하드디스크에 직접 접근하면 중요한 데이터를 덮어쓴다던지하는 문제 발생
	- 하드웨어와 커널의 인터페이스로는 드라이버를 사용
- 인터페이스
	- GUI: 그래픽으로 된 인터페이스
	- CLI: 유닉스나 리눅스 같은 운영체제가 기본적으로 제공하는 인터페이스로 텍스트를 이용해 커널과 상호작용함
- 시스템콜
	- 어플리케이션은 시스템 콜을 통해서 커널에 접근할 수 있음
	- 커널은 사용자로부터 자신을 보호하기 위한 시스템콜이라는 인터페이스를 가지고 있음
- 사용자와 애플리케이션은 커널과의 인터페이스로 시스템콜을 사용하는데 하드웨어와 커널의 인터페이스로는 드라이브를 사용함 

## 컴퓨터 하드웨어와 구조
- 대부분의 컴퓨터는 프로그램 내장 방식의 폰 노이만 구조
	- cpu와 메모리를 두고 이들 사이를 버스로 연결
	- 버스는 데이터를 전달하는 통로
- 프로그램은 메모리에 올려서 실행시키는데 프로그램을 메모리에 내장했다고해서 프로그램 내장 방식이라고 함
- 메모리에 올라간 프로그램은 명령에 따라 처리되고 배선을 바꾸는 대신 소프트웨어만 바꿔주면 되기 때문에 상당히 편해짐


- 컴퓨터 하드웨어
	- 메인보드는 다른 하드웨어를 연결하는 장치
	- 장치 간의 데이터를 전송하는 건 메인보드의 버스가 담당
	- cpu와 메모리는 필수. 이를 메인보드에 꽂음
	- 하드디스크 연결단자에 하드디스크를 꽂음
	- 그래픽카드 연결단자에는 그래픽카드를 꽂음
	- 출력단자에 모니터를 꽂으면 모니터가 작동
	- usb 단자에 마우스와 키보드 연결
	- 사운드 단자에 스피커 연결
- CPU 구조
	- 중앙처리장치
		- 산술 논리연산장치: CPU에서 실제로 데이터 연산을 담당
		- 제어 장치: 모든 장치들의 동작을 지시하고 제어하는 장치
		- 레지스터: CPU내에서 계산을 위해 데이터를 임시로 보관하는 장치
- 메모리 종류
	- RAM: 랜덤으로 데이터를 읽어도 저장된 위치와 상관없이 읽기 속도가 같음
		- 전력이 끊기면 데이터를 잃어버리기 때문에 주로 프로그램을 실행시키는 용도
	- ROM: 전력이 끊겨도 데이터를 계속 보관할 수 있지만 데이터를 한 번 쓰면 수정이 불가능
		- 컴퓨터의 부팅과 관련된 BIOS를 저장하는 데 주로 쓰임

## 컴퓨터의 부팅 과정
- 컴퓨터의 전원을 누르면 ROM에 저장된 BIOS가 실행됨
- BIOS는 전원, CPU, 메모리, 키보드, 마우스, 하드디스크 등 주요 하드웨어에 이상이 없는지 체크함 -> 주요장치에 이상이 있다면 오류음을 내며 부팅이 이뤄지지 않고 이상이 없다면 하드디스크에 있는 마스터 부트 레코드에 저장된 부트로더를 메모리로 가져와서 실행
- 윈도우즈 운영체제와 리눅스 운영체제가 둘 다 설치되어 있는 컴퓨터라면 어떤 운영체제를 선택할지 선택
- 이후로 실행되는 모든 응용프로그램은 메모리에 올라와서 운영체제가 관리

## 인터럽트
- CPU가 입출력 장치에 데이터를 읽거나 쓰려고 하는 상황을 생각해 보자
- 입출력 자극이 들어오면 CPU는 입출력 관리자에게 입출력 명령을 내림
- 폴링 방식
	- CPU관점에선 입출력 명령이 언제 완료될 지 알 수 없기 때문에 주기적으로 입출력 장치에게 계속 확인
	- 주기적으로 확인해줘야하는 과정 때문에 성능이 좋지 않음
- 인터럽트 방식
	- 폴링방식의 단점을 해결한 방식
	- CPU가 입출력 관리자에게 입출력 명령을 내리고 CPU는 다른 작업을 계속함
	- 관리자는 입출력이 완료됐을 때 CPU에게 신호를 주고 CPU는 그 신호를 받아 인터럽트 서비스 루틴을 실행시켜 작업을 완료함
	-  인터럽트 서비스 루틴은 특정 인터럽트가 들어오면 그 인터럽트를 처리하는 함수
	- 인터럽트는 비동기적으로 동작하기 때문에 성능에 이점
- 인터럽트 방식은 하드웨어 방식과 소프트웨어 방식
	- 하드웨어 방식
		- 입출력 등과 같은 인터럽트가 있음
	- 소프트웨어 방식
		- 사용자 프로그램에서 발생한 인터럽트가 있음
		- 유효하지 않은 메모리에 접근하거나 0으로 나누는 명령 등이 있음

## 프로그램과 프로세스
- 프로그램
	- 하드 디스크 등과 같은 저장장치에 저장된 명령문의 집합체
	- 애플리케이션이나 앱이라고도 불리고 윈도우 운영체제에서는 .exe 파일의 모습을 하고 있음
- 프로세스
	- 실행 중인 프로그램
	- 하드디스크에 저장된 프로그램이 메모리에 올라갔을 때 실행중인 프로그램 즉 프로세스라고 불림
	- 프로그램은 컴퓨터 관점에서 하드디스크 즉 저장장치만 사용하는 수동적인 존재
	- 반면 프로세스는 메모리도 사용하고 운영체제의 CPU 스케쥴링 알고리즘에 따라서 CPU도 사용하고 필요에 따라 입력과 출력을 하기 때문에 능동적인 존재라고 말할 수 있음
- 프로세스의 영역
	- 코드 영역: 자신을 실행하는 코드가 저장 
	- 데이터 영역: 데이터 영역은 전역 변수와 static 변수가 저장되어 있음
	- 스택 영역: 지역 변수와 함수를 호출했을 때 필요한 정보들이 저장됨
	- 힙 영역: 프로그래머가 동적으로 메모리를 할당하는 데 쓰임, c언어에서 malloc, free 함수를 호출하면 힙 영역에 자원을 할당, 해제할 수 있음
## 멀티프로그래밍과 멀티프로세싱
- 유니프로그래밍
	- 메모리에 오직 하나의 프로세스가 올라와 처리하는 것
	- CPU는 프로세스를 실행하다가 I/O 작업을 만나면 작업이 완료될 때까지 기다림
	- I/O 작업이 끝나면 작업을 이어서 처리
	- 이 방식은 CPU가 쉬는 시간이 발생, 하나의 프로세스를 다 끝내야 다른 프로세스를 실행할 수 있다는 단점들이 존재
- 멀티프로그래밍
	- 메모리에 여러 개의 프로세스를 올려 이들을 처리
	- CPU가 프로세스를 실행하다가 I/O 작업을 만나면 해당 프로세스에서 발생한 I/O 작업은 기다리면서 다른 프로세스를 실행함
	- cpu가 쉬는 시간이 적어져 결과적으로 효율성 상승
- 멀티태스킹
	- 프로세스가 I/O 작업이 있을 때만 다른 프로세스를 실행하는 방식이 아니라
	- 한 프로세스를 짧게 실행하고 다른 모든 프로세스도 짧게 실행하면서 모든 프로세스를 동시에 실행시키는 것처럼 느끼게 하는 기술
	- 여기서 CPU가 여러개 있다면 이를 멀티프로세서, 그를 이용하는 것을 멀티 프로세싱
## PCB
- 운영체제는 여러 개의 프로세스를 전부관리하고 공평하게 실행시켜야 함
- 프로세스가 만들어지면 운영체제는 해당 프로세스의 정보를 가지고 있는 PCB를 만들고 저장함
- PCB들은 연결리스트라는 자료 구조로 저장됨
- 연결 리스트는 각각의 데이터가 다음 데이터를 연결하는 구조로 되어 있는 자료 구조 
- 운영체제는 프로세스가 종료되면 연결 리스트에서 해당 프로세스의 PCB를 제거함
- PCB의 구조
	- 포인터: 부모와 자식 프로세스에 대한 포인터, 할당된 자원에 대한 포인터, 프로세스의 한 상태에서 다른 상태로 전환될 때 저장하는 포인터
	- 프로세스 상태: 현재 프로세스의 5가지 상태 생성, 준비, 실행, 대기, 완료
	- 프로세스 ID: 프로세스를 식별하기 위한 숫자
	- 프로그램 카운터: 다음에 실행될 명령어의 주소 저장 -> 오늘날 OS는 시분할 처리를 하고 있기 때문에 프로그램 카운터가 꼭 필요함
	- 레지스터 정보: 프로세스가 실행될 때 사용했던 레지스터 값들이 저장됨
	- 메모리 관련 정보: 프로세스가 메모리에 있는 위치 정보, 메모리 침범을 막기 위한 경계 레지스터 값들이 저장
	- CPU 스케쥴링 정보에는 CPU 스케쥴링에 필요한 우선순위, 최종 실행시간, CPU 점유시간 등이 저장됨

## 프로세스 상태
- 오늘날 운영체제는 동시에 수많은 프로세스가 실행됨
- 시분할 시스템을 사용하는 운영체제는 여러 개의 프로세스를 돌아가면서 실행
- CPU가 여러 개의 프로세스를 동시에 실행하는 것이 아니라 한 순간에는 하나의 프로세스 밖에 처리하지 못하나 속도가 매우 빨라서 동시에 실행하는 것 처럼 보이는 것
- 프로세스에는 시분할 시스템을 처리하기 위해 5가지 상태가 존재
	- 생성 상태: PCB를 생성하고 메모리에 프로그램 적재를 요청한 상태
	- 준비 상태: 프로그램 적재가 승인되면 준비상태, CPU를 사용하기 위해 기다리고 있는 상태 -> CPU 스케쥴러에 의해 CPU가 할당됨
	- 실행 상태: 준비 상태에 있는 프로세스가 CPU스케쥴러에 의해 CPU를 할당받아 실행되는 상태, 실행 상태에 있는 프로세스의 수는 CPU의 개수만큼
	- 대기 상태: 프로세스가 입출력 요청을 하면 입출력 완료될 때 까지 기다리는 상태
	- 완료 상태: 프로세스가 종료된 상태, 프로세스가 사용했던 데이터를 메모리에서 제거하고 생성된 PCB도 제거

## 컨텍스트 스위칭
- 컨텍스트 스위칭은 프로세스를 실행하는 중에 다른 프로세스를 실행하기 위해 실행 중인 프로세스의 상태를 저장하고 다른 프로세스의 상태 값으로 교체하는 작업
- 컨텍스트 스위칭이 일어날 때 PCB의 내용 변경
- 실행 중인 프로세스의 작업을 PCB에 저장하고 실행될 기존 프로세스의 PCB 내용대로 CPU가 다시 세팅됨
- 컨텍스트 스위칭이 일어날 때 PCB에 변경하는 값들로는 프로세스 상태, 다음 실행할 명령어의 주소를 담고 있는 프로그램 카운터, 각종 레지스터 값 등이 있음

- 프로세스 2개가 컨텍스트 스위칭을 하는 상황을 생각해보자
- 프로세스 A가 먼저 실행하는데 CPU 점유시간 초과 -> 운영체제는 프로세스 A가 CPU를 너무 오래 사용했다고 판단하고 인터럽트 발생
- 프로세스 A는 하던 일을 멈추고 현재 CPU의 레지스터 값 등을 PCBA에 저장
- PCB B를 참조해서 이전 프로세스 B의 상태로 CPU 레지스터 값을 설정
- 여기에는 다음 실행할 명령어의 주소를 가지고 있는 프로그램 카운터를 가지고 있기 때문에 바로 프로세스 B의 명령어 실행 가능
- PCB B또한 점유시간을 초과하면 운영체제는 다시 인터럽트 발생시킴
- cpu는 프로세스 B의 상태를 PCB B에 저장하고 PCB A에서 다시 프로세스 A의 상태를 가져오고 다시 프로세스 A를 실행시킴
- 이런식으로 메모리에 있는 모든 프로세스들은 컨텍스트 스위칭을 함

## 프로세스 생성과 종료
- 컴퓨터가 부팅되면 운영체제는 최초의 프로세스 하나를 생성
- 이 프로세스는 0번이라는 식별자가 부여되어 0번 프로세스라고 불림
- 운영체제에 필요한 다른 프로세스들은 새로 생성하는 대신 이 0번 프로세스를 복사하여 생성
- 일반 애플리케이션 역시 자신이 실행되는 계층의 부모 프로세스를 복사해 실행됨

- 리눅스애서 vim을 실행하는 과정을 생각해보자
- 터미널에서는 Bash가 사용자의 명령어를 해석하고 실행함
- 사용자가 터미널에 vim 명령어를 입력하면 bash 프로세스가 fork 함수를 사용해 자신을 복사해 vim 프로세스를 생성함
- 새로 생성하는 것 보다 프로세스를 복사하는 것이 더 저렴하기 때문에 이 방식
- 이 때 복사된 프로세스를 자식 프로세스라고 하며 자식 프로세스 입장에서 자신을 복사한 프로세스는 부모 프로세스
- 자식 프로세스는 부모 프로세스의 코드 영역, 데이터 영역, 스택 영역과 PCB의 내용을 모두 복사함 -> 부모 프로세스와 동일하게 실행됨
- 따라서 원하는 함수를 실행하기 위해 운영체제에서 제공하는 exec함수를 이용함
- fork함수로 프로세스를 복사한 후 exec함수를 실행하면 복사된 자식 프로세스의 코드와 데이터 영역이 원하는 값으로 덮어쓰여짐 -> 부모프로세스와 완전히 다른 동작 수행

## 쓰레드
- 운영체제가 작업을 처리하는 단위는 프로세스
- 사용자가 운영체제에게 작업을 요구하면 그만큼 프로세스의 수가 늘어남
- 프로세스를 생성하면 PCB가 생성되고 메모리에 코드, 데이터, 스택, 힙 영역을 만들어줘야 함
- 프로세스의 수가 많아지면 프로세스의 수만큼 PCB, 코드, 데이터, 스택, 힙 영역도 만들어줘야하기 때문에 너무 무거워짐

- 쓰레드는 프로세스 내에 존재, 1개 이상이 있을 수 있음
- 쓰레드들은 그 프로세스의 PCB, 코드, 데이터, 힙 영역을 공유함
- 스택은 공유하지 않고 각각 가지고 있음
- 쓰레드 ID로 쓰레드들을 구분하고 관리하기 위한 TCB -> 운영체제 관점에서 쓰레드도 구분이 가능해짐
- 운영체제가 작업을 처리하는 단위는 프로세스 내의 쓰레드가 됨

- 장단점
	- 프로세스는 서로 독립적이기 때문에 하나의 프로세스가 문제가 있더라도 다른 프로세스가 영향을 받지 않음 -> 안전성 우수
	- 쓰레드는 하나의 프로세스 내에 존재하기 때문에 해당 프로세스에 문제가 생기면 그 안에 있는 모든 쓰레드에 문제가 생김

	- 각각의 프로세스는 고유한 자원, 프로세스 간 통신을 하려면 IPC를 이용해야 해서 오버헤드가 크고 속도가 느림
	- 쓰레드는 한 프로세스 내에서 스택 영역을 제외한 모든 영역을 공유하기 때문에 오버헤드가 굉장히 작음
	- 쓰레드 간 통신은 데이터를 공유할 수 있기에 쉽게 할 수 있지만 공유되는 공간에서 문제가 발생할 수 있음

## CPU 스케쥴링 개요
- 컴퓨터의 자원 구분
	- CPU와 메모리 같은 필수장치
	- 하드디스크나 키보드, 마우스와 같은 주변장치

- 프로그램을 실행시키면 메모리에 프로세스가 생성되고 각 프로세스에는 한 개 이상의 쓰레드
- 프로세스들은 CPU를 차지하기 위해 운영체제의 명령을 기다림
- 운영체제는 모든 프로세스에게 CPU를 할당/ 해제 하는데 이를 CPU 스케쥴링이라 함
- CPU 스케쥴링에서 스케쥴러가 고려해야 할 상황은 두 가지
	- 어떤 프로세스에게 CPU리소스를 줘야 하는가 -> CPU 사용권을 줘야하는가
	- CPU를 할당받은 프로세스가 얼마의 시간동안 CPU를 사용해야 하는가 -> 오늘날은 시분할 처리 방식으로 여러 프로세스에서 짧은 시간동안 돌아가며 CPU 할당
- CPU를 할당받아 실행하는 작업을 CPU 버스트
- 입출력 작업을 I/O 버스트

## 다중큐
- 프로세스가 생성되면 준비 상태로 전환되고 준비 상태에서 CPU를 기다리고 있는 프로세스들은 CPU 스케쥴러에 의해 실행 상태로 전환됨
- 실행 상태에 있는 프로세스는 CPU 할당 시간이 다 됐다면 다시 준비 상태로 전환되고 I/O 요청이 있다면 대기 상태로, 작업이 끝났다면 완료 상태로 전환됨
- 프로세스가 대기하고 있는 준비상태와 대기상태는 큐 라는 자료 구조로 관리
	- 큐 자료구조는 FIFO
- CPU 스케쥴러는 준비 상태의 다중큐에 들어있는 프로세스들 중에 적당한 프로세스를 선택해서 실행상태로 전환시킴
- 프로세스가 실행 상태에서 I/O 요청을 받아 대기 상태로 오게 되면 I/O 작업 종류에 따라서 분류된 큐에 들어가게 됨
- 예를 들어 하드디스크 작업은 HDD 큐에 들어가고 하드디스크 작업이 완료되어 인터럽트가 발생되면 HDD큐를 뒤져서 다시 꺼내감
- 정확히 말하면 큐에 들어가는 것은 프로세스의 정보를 가지고 있는 PCB

- 정리
- 프로세스 정보를 담고 있는 PCB는 준비상태의 다중큐에 들어가서 실행되기를 기다림
- CPU 스케쥴러는 준비 상태의 다중큐를 참조해서 어떤 프로세스를 실행시킬지 정하고 정해진 프로세스가 실행상태로 전환
- 실행 중인 프로세스에서 I/O 작업이 발생하면 해당 I/O 작업의 종류별로 나뉜 큐에 들어가고 CPU 스케쥴러는 이를 참조해 스케쥴링을 함

## 스케쥴링의 목표
- 리소스 사용률
	- CPU 사용률을 높이는 것을 목표로 할 수도 있고, I/O 디바이스의 사용률을 높이는 것을 목표로 할 수도 있음
- 오버헤드 최소화
	- 스케쥴링을 하기 위한 계산이 너무 복잡하거나 컨텍스트 스위칭을 너무 자주하면 오버헤드가 너무 커짐
	- 스케쥴러는 이를 최소화하려고 함
- 공평성
	- 모든 프로세서에게 공평하게 CPU가 할당되어야 함
	- 공평의 의미는 시스템에 따라 달라질 수 있음
- 처리량
	- 같은 시간 내에 최대한 많은 처리를 할 수 있는 방법을 목표로 함
- 대기시간
	- 작업을 요청하고 실제로 작업이 이뤄지기 전까지 대기하는 시간이 짧은 것을 목표로 함
- 응답시간
	- 대화형 시스템에서 사용자의 요청이 얼마나 빨리 반응하는지가 중요하기 때문에 응답시간이 짧은 것을 목표로 함

- 목표를 달성하기 위해서 상반되는 상황 때문에 모두를 최상의 컨디션으로 유지하기는 어려움
	- ex) 처리량을 높이기 위해서는 하나의 프로세스에 CPU를 오래 할당해야 함, 반면 응답시간을 줄이기 위해서는 여러 프로세스에 골고루 CPU를 할당해야 함 -> 처리량과 응답시간의 목표를 같이 달성하기 어려움

## FIFO 알고리즘
- 먼저 들어온 작업이 먼저 나간다
- 스케쥴링 큐에 들어온 순서대로 CPU 할당
- 먼저 들어온 프로세스가 완전히 끝나야만 다음 프로세스가 진행
- 단순하고 직관적이나 실행시간이 짧고 늦게 도착한 프로세스가 실행 시간이 길고 먼저 도착한 프로세스 작업을 기다려야 한다는 단점
- I/O 작업이 있다고 하면 그 작업이 끝날 때까지 기다려야 하기 때문에 CPU 효율성이 떨어짐
- 스케쥴링의 성능은 평균 대기시간으로 평가함
- 프로세스가 여러개 실행 될 때 프로세스들의 모든 대기 시간의 평균을 말함
- 작업 순서에 따라 평균 대기 시간이 크게 달라질 수 있음
-   FIFO는 도착 순서대로 처리하기 때문에, 짧은 작업이 긴 작업 뒤에 줄 서면 '콘보이 효과'가 발생해 대기 시간이 길어짐

## SJF 알고리즘
- 버스트 타임이 짧은 프로세스 먼저 실행됨
- fifo 보다 성능이 좋으나 문제점 두가지
	- 어떤 프로세스가 얼마나 실행될지 예측하기 힘듦
	- 버스트 타임이 긴 프로세스는 아주 오랫동안 실행되지 않을 수도 있음

## RR 알고리즘
- fifo 알고리즘은 일괄처리 시스템에 적절해서 시분할 처리 시스템에서는 쓰기가 힘듦
- sjf 알고리즘도 위에 언급한 문제점이 있음

- fifo 알고리즘의 가장 큰 문제는 먼저 들어온 프로세스가 끝나야 다음 프로세스가 진행 된다는 것
- 이 문제를 해결하기 위해 한 프로세스에 일정 시간만큼 cpu를 할당하고 할당된 시간이 지나면 강제로 다른 프로세스에 일정시간만큼 cpu를 할당함
- 강제로 cpu를 뺏긴 프로세스는 큐의 가장 뒷 부분으로 밀려남
- 프로세스에게 할당하는 일정 시간은 타임 슬라이스 또는 타임 퀀텀이라고 부름

## MLFQ
- 가장 일반적으로 쓰이는 기법
- RR의 업그레이드 된 알고리즘
- 기본적으로 CPU 사용률과 I/O 사용률이 좋게 나오는 작은 크기의 타임 슬라이스를 선택함
- CPU 바운드 프로세스들에는 타임슬라이스를 크게 줌

- 이를 운영체제가 어떻게 구분하는가
- CPU를 사용하는 프로세스가 실행하다가 스스로 CPU를 반납하면 CPU 사용이 적은 것이니 I/O 바운드 일 확률이 높음
- 반대로 CPU를 사용하는 프로세스가 타임 슬라이스 크기를 오버해서 CPU 스케쥴러에 의해 뺏기는 상황이면 CPU사용량이 많은 것이니 CPU 바운드일 확률이 높음
- MLFQ는 여러 우선순위 큐를 두고, 프로세스의 CPU 사용 패턴에 따라 큐 간 이동시키며 적절한 시간 할당량을 부여해 효율성을 높임

## 프로세스 간 통신 IPC
- IPC의 방식
	- 메세지 전달 방식: 한 프로세스가 다른 프로세스와 메모리를 공유하지 않고 데이터를 전달하는 방식 -> 파이프/ 메세지 큐/ 소켓
		- 파이프: 운영체제가 생성한 통로를 통해 한 프로세스가 다른 프로세스에게 데이터를 전송하거나 읽는 방식, 스트림형태의 단방향 통신이므로 송신 프로세스와 수신 프로세스가 반드시 동시에 실행되어야 함
		- 메세지 큐: 송신 프로세스가 보낸 데이터를 임시 저장소인 큐에 보관했다가 수신 프로세스가 필요할 때 가져가는 방식, 양방향 통신이 가능해 두 프로세스가 동시에 실행될 필요가 없음
		- 소켓: 클라이언트 서버 구조로 이뤄짐, 같은 컴퓨터 뿐아니라 다른 네트워크의 프로세스와도 통신할 수 있음, 양방향 통신과 비동기 통신이 모두 가능
	- 공유 메모리 방식: 프로세스가 메모리를 공유하여 데이터를 직접 읽고 쓰면서 통신하는 방식 -> 세마포어/ 뮤텍스/ 모니터
		- 이러한 방식은 메모리를 공유하는 과정에서 버그가 발생하는 동기화 문제 가능성
		- 동일한 프로세스 내에서 메모리를 공유하는 쓰레드에서도 나타남
	- 시그널
	- 파일
	- 원격 프로시저

## 공유자원과 임계구역
- 프로세스 간 통신을 할 때 공통으로 이용하는 변수나 파일들을 공유자원이라고 함
- 공유자원은 여러 프로세스가 공유하고 있기 때문에 각 프로세스의 접근 순서에 따라 결과가 달라질 수 있음
- 컨텍스트 스위칭으로 시분할 처리를 하기 때문에 어떤 프로세스가 먼저 실행되고 어떤 프로세스가 나중에 실행되는지 예측하기 힘듦
- 연산결과를 예측하기 힘들고 여기서 발생하는 문제를 동기화 문제라고 함
- 이를 해결하기 위해 여러 프로세스가 동시에 사용하면 안되는 영역인 임계구역을 정의함
- 공유자원을 서로 사용하기 위해 경쟁하는 것은 경쟁 조건이라고 함
- 임계구역 문제를 해결하기 위해서는 상호배제 메커니즘이 필요
- 상호배제의 요구사항
	- 임계구역엔 동시에 하나의 프로세스만 접근한다
	- 여러 요청에도 하나의 프로세스의 접근만 허용한다
	- 임계구역에 들어간 프로세스는 빠르게 나와야 함

## 세마포어
- 상호배제 메커니즘의 하나
- 정수형 변수
- 세마포어 선언
- 공유 자원에 대한 동시 접근을 제어하여 임계 구역 문제를 해결하는 가장 기본적인 동기화 도구
- `wait`와 `signal` 연산을 통해 임계 구역에 한 번에 하나의 프로세스만 접근하도록 상호 배제를 구현
- 모니터
	- 세마포어의 단점을 해결한 상호 배제 메커니즘
	- 따로 운영체제에서 처리하는 것이 아니라 프로그래밍 언어 차원에서 지원하는 방법

## 데드락(교착상태)
- 여러 프로세스가 서로 다른 프로세스의 작업이 끝나기를 기다리다가 아무도 작업을 진행하지 못하는 교착 상태
- 교착상태는 공유자원 때문에 발생 -> 서로 차지하려다가 
- 교착상태의 필요조건 (이 조건들 중 하나라도 충족되지 않으면 교착상태가 발생하지 않음)
	- 상호배제: 어떤 프로세스가 한 리소스를 점유했다면 그 리소스는 다른 프로세스에게 공유되면 안됨
	- 비선점: 프로세스 A가 리소스를 점유하고 있는데 프로세스 B가 리소스를 빼앗을 수 없어야 함
	- 점유와 대기: 어떤 프로세스가 리소스 A를 가지고 있는 상태에서 리소스 B를 원하는 상태여야 함
	- 원형대기: 점유와 대기를 하는 프로세스들의 관계가 원형을 이루고 있다는 것

## 데드락 해결
- 프로세스들에게 자원을 할당할 떄 어느 정도 자원을 할당해야 교착상태가 발생하는지 파악해서 교착상태가 발생하지 않는 수준의 자원을 할당함
- 교착상태 회피는 전체 자원의 수와 할당된 자원의 수를 기준으로 안정상태와 불안정상태로 나눔
- 운영체제는 최대한 안정상태를 유지하려고 자원을 할당
- 불안정상태에 있더라도 무조건 교착상태에 빠지는 것이 아니라 교착상태에 빠질 확률이 높아지는 것
- 운영체제는 프로세스들에게 자원을 할당하기 전에 자기가 가지고 있는 전체 자원의 수를 알고 있어야 함(총자원)
- 프로세스들은 각자 자기가 필요한 자원의 최대 숫자를 운영체제에게 알려줘야 함(최대 요구 자원)

- 가벼운 교착상태 검출
	- 타이머를 이용
	- 프로세스가 일정시간동안 작업을 진행하지 않는다면 교착상태가 발생했다고 간주하고 이를 해결
	- 일정 시점마다 체크포인트를 만들어 작업을 저장하고 타임아웃으로 교착상태가 발생했다면 마지막으로 저장했던 체크포인트로 롤백하기
	- 억울하게 종료되는 프로세스가 생길 수 있음
- 무거운 교착상태 검출
	- 자원할당 그래프 이용
	- 현재 운영 체제에서 프로세스가 어떤 자원을 사용하는지 지켜보고 교착 상태가 발생했다면 해결
	- 교착 상태를 검출했다면 교착 상태를 일으킨 프로세스를 강제 종료
	- 다시 실행시킬 때 체크포인트로 롤백
	- 이 방식은 운영체제가 지속적으로 자원할당 그래프를 유지하고 검사해야 하기 때문에 오버헤드가 발생 -> 그러나 억울하기 종료되는 프로세스가 발생하지 않음
## 컴파일과 프로세스
- 코드가 어떻게 프로세스가 되고 메모리에 할당되는지
- 프로그래밍 언어는 컴파일언어/ 인터프리터 언어로 구분
- 컴파일 언어
	- 개발자가 코드를 작성하고 컴파일이라는 과정을 거쳐서 0과 1로 된 기계어로 실행 파일을 만듦
	- 컴파일 과정에서 개발자가 문법 오류를 일으켰는지 검사하고 CPU에서 처리 가능한 기계어로 실행 파일을 만들어 놓기 때문에 속도가 빠름
- 인터프리터 언어
	- 개발자가 작성한 코드를 미리 기계어로 만들지 않고 실행 시 코드를 한 줄 씩 해석해 실행하는 언어
	- 미리 검사를 하지 않기 때문에 오류가능성과 속도도 느림

- 프로세스의 메모리영역
	- 코드영역: 실행해야 할 코드가 들어가는 영역
	- 데이터영역: 전역 변수나 배열이 들어가는 영역
	- 스택 영역/ 힙 영역: 프로세스가 실행될 때 할당되는 메모리로 스택에는 지역 변수와 함수 관련 값들이 들어가고 힙은 실행 중에 메모리 공간을 할당할 수 있는 유동적인 공간 

## 메모리의 종류
- 여러 종류의 메모리
- 레지스터
	- 가장 빠른 기억 장소로 CPU내에 존재
	- 컴퓨터의 전원이 꺼지면 데이터가 사라지기 때문에 휘발성 메모리
	- 32비트 cpu/ 64 비트 cpu라고 힐 때 비트는 레지스터의 크기를 말함
	- CPU는 계산을 할 때 메인 메모리에 있는 값을 레지스터로 가져와 계산 
	- 계산 결과는 다시 메인 메모리에 저장
- 메인 메모리(RAM)
	- 레지스터와 메인 메모리 사이에는 캐시라는 휘발성 메모리
	- 매우 느린 속도의 메인 메모리
	- 메인 메모리에 있는 값을 레지스터로 옮기려면 한참 걸리기 때문에 필요할 것 같은 데이터를 미리 가져와 저장하는 곳이 바로 캐시
	- 실제 운영체제와 다른 프로세스들이 올라가는 공간인 메인 메모리
	- 전원이 공급되지 않으면 데이터가 지워지기 때문에 휘발성 메모리
	- 하드디스크나 SSD보다 속도는 빠르지만 가격이 비싸기 때문에 데이터를 저장하기보다는 실행중인 프로그램만 올림
- 보조저장장치 (HDD, SSD)
	- 하드디스크
	- 가격이 저렴하고 전원이 공급되지 않아도 데이터가 지워지지 않는 비휘발성 메모리

## 메인메모리와 주소
- 오늘 날 컴퓨터는 폰 노이만 구조
- 폰 노이만 구조는 모든 프로그램을 메인 메모리에 올려 실행
- 유니프로그래밍 환경에선 하나의 프로그램만 메모리에 올라오기 때문에 메모리 관리가 어렵지 않으나, 멀티 프로그래밍 환경에서는 여러 프로그램이 올라오니 복잡
- 32비트 CPU
	- 레지스터 크기가 32비트
	- CPU가 처리하는 ALU도, 데이터가 이동하는 버스도 32비트
	- CPU가 다룰 수 있는 메모리도 2의 32승으로 4GB
- 64비트 CPU
	- 레지스터, ALU, 버스 모드 64비트
	- 다룰 수 있는 메모리도 2의 64승으로 거의 무한대 
	- 한 번에 처리할 수 있는 양이 많기 때문에 속도가 더 빠름
- 물리주소 공간
	- 메모리를 컴퓨터에 연결하면 0번지부터 시작하는 주소공간
	- 사용자 관점에서 바라본 주소공간은 논리 주소 공간이라고 부름
	- 사용자는 물리 주소를 몰라도 논리 주소로 물리 주소에 접근할 수 있음
	- 메모리에는 운영체제와 수많은 프로세스가 올라옴
	- 그 중 운영체제를 위한 공간은 따로 마련 -> 악의적인 프로그램으로 운영체제를 침범하는 것을 방지하려고
	- 하드웨어적으로 운영체제 공간과 사용자 공간을 나누는 경계 레지스터
- 절대주소와 상대주소
	- 절대주소: 실제로 프로그램이 올라간 주소, 메모리 관리자가 바라본 주소인 절대 주소는 물리 주소 공간
	- 상대주소: 사용자가 바라본 주소, 논리 주소 공간
- 메모리 관리자

## 메모리 할당방식
- 크게 두가지로 나눌 수 있음
- 고정 분할 메모리 할당
	- 메모리를 고정된 크기로 분할하여 각 영역에 하나의 프로세스를 할당하는 방식
	- 프로세스의 크기가 분할된 크기보다 작으면 공간이 낭비되는 내부단편화 발생
	- 프로세스의 크기가 분할된 크기보다 크면 실행이 불가능하다는 단점
- 가변 분할 메모리 할당
	- 메모리를 프로세스의 크기에 맞춰 유동적으로 할당하는 방식
	- 프로세스 크기에 맞게 메모리를 분할하므로 내부 단편화 X
	- 남은 메모리 공간의 총합은 충분하지만 이들이 연속되지 않아 프로세스를 실행할 수 없는 외부 단편화 발생
- 두 방식 모두 연속된 메모리 공간이 없으면 프로세스를 실행할 수 없음 -> 두 방식은 연속 메모리 할당으로 분류됨
- 연속 메모리 할당
	- 과거 운영체제에서 사용되던 방식으로 현재는 임베디드와 같은 특수한 환경에서만 사용됨

## 가상메모리
- 프로세스는 운영체제 영역이 어디 있는지, 물리 메모리의 크기가 얼마나 큰지 몰라도 됨
- 즉 프로그래머는 물리 메모리의 크기와 프로세스가 메모리의 어느 위치에 올라가는지 신경쓰지 않고 0번지에서 시작한다고 생각하고 프로그래밍을 하면 됨
- 프로세스는 메모리 관리자를 통해 메모리에 접근 
- 프로세스 입장에서는 물리 메모리에 직접 접근할 일이 없고 메모리 관리자에게 요청만 하면 됨
- 메모리 관리자는 프로세스의 요청이 있다면 그에 맞는 물리 메모리로 연결시켜 줌
- 가상 메모리의 크기는 이론적으로는 무한대이지만 실제로는 물리 메모리의 크기와 CPU의 비트수로 결정됨
- 가상 메모리는 하드디스크 내 스왑 영역에 현재 실행시키지 않는 프로세스를 옮겨두고 처리가 필요할 때 물리 메모리로 가져와 실행시키기 때문에 운영체제와 프로세스들을 전부 실행시킬 수 있음
- 메모리 관리자는 물리 메모리와 스왑 영역을 합쳐서 프로세스가 사용하는 가상 주소를 물리 주소로 변환하는데 이를 동적 주소 변환이라고 함
- 메모리 관리자는 물리 메모리를 어떻게 나눌지, 프로세스를 어디다 배치할지, 부족한 물리 메모리는 어떻게 처리할지와 같은 문제를 처리해야 하기 때문에 복잡한 과정을 거침
- 가상 메모리 시스템에서는 운영체제 영역을 제외한 나머지 영역을 일정한 크기로 나누어서 프로세스에게 할당
- 할당하는 방식은 메모리 분할 방식과 마찬가지로 가변분할방식(세그멘테이션)과 고정분할방식(페이징)이 있음
- 세그멘테이션-페이징 혼용기법
- 가상 메모리 시스템에서 가상 주소는 메모리나 스왑 영역 한 곳에 위치
- 메모리 관리자는 가상 주소와 물리 주소를 1대1 매핑 테이블로 관리

## 세그멘테이션(배치정책)
- 가변 분할 방식
- 세그멘테이션에서 프로그램은 함수나 모듈등으로 세그먼트 구성
- 메모리 = > 메인 코드가 있는 세그먼트, 전역 데이터가 있는 세그먼트, 힙, 스택 영역이 있는 세그먼트 등이 있음 
- 메모리 안에서 각 세그먼트들이 서로 인접할 필요는 없음
- 반면 프로세스 입장에서는 각 스택들이 인접한 것 처럼 바라봄

- 메모리 관리자가 논리 주소를 물리 주소로 바꾸는 법
- 메모리 관리자는 세그멘테이션 테이블에 저장된 베이스 어드레스와 바운드 어드레스를 통해서 물리 주소로 바꿈
- CPU에서 논리주소를 전달해주면 메모리 관리자는 이 논리 주소가 몇 번 세그먼트인지 알아냄
- 그리고 메모리 관리자 내의 세그먼트 테이블 베이스 레지스터를 이용해서 물리 메모리 내에 있는 세그멘테이션 테이블을 찾고, 세그먼트 번호를 인덱스로 베이스 어드레스와 바운드 어드레스를 찾아냄
- 이때 운영체제는 컨텍스트 스위칭을 할 때마다 메모리 관리자 내의 세그먼트 테이블 베이스 레지스터를 해당 프로세스의 것으로 값을 바꿔줘야 함
- 이 방식은 외부단편화 발생 가능성

## 페이징(배치정책)
- 세그멘테이션 기법은 외부단편화 문제가 있기 때문에 이를 해결하기 위해 고안됨
- 페이징은 메모리를 할당할 때 정해진 크기의 페이지로 나눔
- 일정한 크기로 나눴기 때문에 외부단편화 현상이 일어나지 않음
- 논리주소 공간을 동일한 크기의 페이지로 나누고 물리 주소 공간은 프레임으로 나눔

- 메모리 관리자가 논리 주소를 물리 주소로 바꾸는 법
- 메모리관리자는 인덱스와 프레임 번호로 구성된 페이지 테이블을 가짐
- CPU에서 논리 주소를 전달해주면 메모리 관리자는 이 논리주소가 몇 번 페이지인지, 오프셋은 얼마인지 알아냄
- 메모리 관리자 내 페이지 테이블 레지스터를 이용해서 물리 메모리에 있는 페이지 테이블을 찾고 페이지 번호를 인덱스로 프레임번호를 알아내고 오프셋을 이용해 물리 주소를 알아냄
- 이때 운영체제는 컨텍스트 스위칭을 할 때마다 메모리 관리자 내의 페이지 테이블 베이스 레지스터를 해당 프로세스의 것으로 값을 바꿔줘야 함
- 내부단편화 발생 가능성
- 세그멘테이션은 논리적인 영역별로 세그먼트를 나눔 세그먼트마다 크기를 다르게 나눌 수 있음
- 페이징은 크기가 고정되어 있어 논리적인 영역별로 나누는 것이 아니라 페이지로 나누기 때문에 논리적인 영역을 나눌 수 없음 -> 특정 영역별로 나눌 수 없음
## 페이지드 세그멘테이션(배치정책)
- 세그멘테이션과 페이징을 혼합해 장점을 취한 방식
- 세그멘테이션은 가변 분할 방식이라서 코드 영역, 데이터 영역 등을 세그먼트로 나눠서 관리 -> 다른 프로세스와 공유도 편하고 각 영역에 대한 메모리 접근보호를 하기 쉬움
- 페이징은 고정분할방식으로 메모리를 효율적으로 관리할 수 있음

- 메모리 접근 권한은 메모리의 특정 번지부터 부여된 권한으로 읽기, 쓰기, 실행이 있음
- 프로세스는 각 영역마다 접근 권한이 있음
- 코드 영역은 프로그램 그 자체이므로 수정되면 안되기 때문에 읽기/ 실행 권한
- 데이터 영역은 일반 변수, 전역 변수, 상수로 선언된 변수가 저장되기 때문에 읽기 권한 혹은 쓰기 권한까지 
- 스택과 힙 영역은 읽기/ 쓰기 권한
- 메모리 접근 권한에 대한 검사는 가상 주소에서 물리 주소로 변환 될 때마다 일어나는데 만약 권한을 위반하면 에러를 발생시킴

- 페이지드 세그멘테이션 기법에선 세그멘테이션 테이블에 권한비트를 추가
- 베이스 어드레스는 페이지 넘버로 바귀고 바운드 어드레스는 페이지 개수로 바뀜
- 각 역할은 이름만 달라졌을 뿐 본질적으로 달라진 것은 없음

- 가상 주소가 들어오면 가상 주소를 이용해 몇 번 세그먼트인지 알아냄
- 해당 세그먼트가 메모리 접근 권한을 위반하는지 체크하고 위반하면 종료
- 위반하지 않으면 페이지 넘버와 개수를 가져옴
- 페이지 넘버로 페이지 테이블에 접근해서 프레임 번호를 가져오고 물리 메모리 내 해당 프레임에 접근해서 그 위치에서 논리주소에서 알아낸 오프셋을 더함
- 만약 물리 물리 메모리에 해당 프레임이 없다면 스왑 영역에서 가져옴
- 단점은 물리 메모리에 접근하기 위해선 메모리에 접근을 두 번 해야 한다는 것
	- 첫 번째는 세그멘테이션 테이블을 참조할 때
	- 두 번째는 페이지 테이블을 참조할 때

## 디맨드 페이징(가져오기 정책)
- 프로세스가 실행될 때 필요한 모듈만 올라와서 실행됨
- 지역성 이론
	- 공간의 지역성: 현재 위치와 가장 가까운 데이터에 접근할 확률이 높음
	- 시간의 지역성: 최근 접근했던 데이터가 오래 전에 접근했던 데이터보다 접근할 확률이 높음
	- 지역성 이론은 지금 당장 쓰일 데이터만 메모리에 올리고 당분간 필요하지 않을 것 같은 데이터는 스왑 영역으로 보내 성능을 향상시킴
- 메모리 계층 구조
	- 메모리는 레지스터, 캐시, 메인 메모리, 보조저장장치로 구성
	- 레지스터에서 보조저장장치로 갈수록 메모리에 접근하는 시간이 느려짐
	- 가상 메모리의 크기는 물리 메모리에 스왑 영역을 합친만큼
	- 스왑 영역에서 물리 메모리로 데이터를 가져오는 것을 스왑인이라고 부르고 물리 메모리에서 스왑 영역으로 데이터를 보내는 것을 스왑 아웃이라고 부름 -> 이것을 판단하는 것을 페이지 교체 알고리즘
- 페이지 테이블 엔트리
	- 접근비트: 읽거나 실행했으면 비트가 1로
	- 변경비트: 쓰기가 일어나면 비트가 1로
	- 유효비트: 유효비트가 1이면 페이지가 물리 메모리, 0이면 스왑 영역
	- 읽기/쓰기/실행 비트: 권한비트로 해당 메모리에 접근 권한이 있는지 점검
	- 프레임 
- 프로세스가 가상 메모리에 접근 요청을 했을 때 메모리 관리자는 페이지 테이블을 보고 물리 메모리의 프레임을 찾아내는데 없으면 Page fault라는 인터럽트를 발생시킴 -> 보조장치의 스왑영역에 접근하고 프로세스는 대기상태가 됨 -> 스왑영역에 있는 데이터가 메모리 영역에 올라감 -> 프로세스가 다시 실행

## 페이지 교체 정책
- 메모리가 꽉 찼을 때 어느 메모리를 스왑영역으로 보낼지 결정하는 것
- 프로세스는 데이터 접근을 위해 메모리를 참조하는데 해당 페이지가 메모리에 없으면 page fault 발생
- page fault가 발생하면 해당 페이지를 스왑 영역에서 메모리로 불러들여야 하는데 메모리가 꽉 차서 공간이 없다면 메모리에 있는 페이지를 스왑영역으로 옮겨야 함
- 어떤 페이지를 옮길지 선택하는 것을 페이지 교체 정책

- 무작위 선택 방식
	- 지역성을 고려하지 않아 자주 사용되는 페이지도 선택될 수 있어 성능이 좋지 않음
- FIFO
	- 메모리에 가장 오래 머물러있는 페이지를 선택하는 방식
	- 메모리에 가장 먼저 들어온 페이지를 가장 먼저 교체
	- 선입 선출 방식
	- 빌레이디의 역설이 가장 큰 문제
	- 하드웨어적으로 접근비트를 이용하지 않는 환경에서는 FIFO사용
	- FIFO를 개선한 2차 기회 페이지교체 알고리즘 구현
		- 자주 사용한 페이지에는 또 한 번의 기회
		- FIFO와 동일하게 동작하지만, 만약 page fault 없이 페이지 접근에 성공했다면, 해당 페이지를 큐의 맨 뒤로 이동시켜 수명 연장
- optimum
	- 앞으로 가장 오랫동안 쓰이지 않을 페이지를 선택하는 방법
	- 그러나 구현이 불가능한 이론적인 방법
	- 다른 알고리즘과 성능을 비교할 때 참조용
- LRU
	- 가장 최근에 사용되지 않은 페이지를 선택하는 방법
	- 지역성 이론의 시간의 지역성에 따르면 최근 사용한 데이터가 앞으로도 사용될 확률이 높음 -> 최근에 사용하지 않은 페이지가 앞으로도 사용될 확률이 적음
	- 프로그램이 지역성을 띄지 않으면 사용성이 떨어짐
	- 시간을 기록해야하는데 그러면 비트가 많이 필요해서 구현이 힘듦
	- 이 때문에 클락 알고리즘 구현
- 빌레이디의 역설
	- page fault를 줄이려고 메모리를 더 늘려서 프레임의 수를 늘려놨는데 오히려 더 발생하는 역설
	- FIFO에서만 발생
- 클락 알고리즘
	- 접근 비트 하나만 이용
	- 일정 시간 간격마다 모든 페이지의 접근 비트를 0으로 초기화
	- 비트의 초기값은 0으로 설정, 페이지가 참조되었다면 1로 설정
	- 일정 시간 간격마다 페이지가 참조되었는지 아닌지 판단가능
	- 클락 알고리즘은 페이지를 원형으로 연결
	- 스왑 영역으로 옮길 페이지를 포인터로 가리키는데 이를 클락 핸드라고 부름
	- 클락 핸드는 시계방향으로 움직임
	- 움직이면서 접근비트가 0인 비트를 발견하면 해당 페이지를 스왑 영역으로 보냄
- 향상된 클락 알고리즘
	- 접근비트와 변경비트까지 봄
	- 접근비트가 0 변경 0, 접근비트가 0 변경비트가 1 ~ 접근비트가 1 변경비트가 1 순서대로 변경 

## 쓰레싱과 워킹셋
- cpu 스케쥴링의 목표는 cpu 사용률을 높이는 것
- 높이기 위해선 동시에 사용되는 프로그램의 수, 즉 멀티 프로그래밍의 정도를 높이는 것
- 동시에 실행하는 프로세스의 수가 늘어나면 어떤 프로세스가 I/O 작업으로 cpu 사용을 할 수 없을 때 다른 프로세스로 컨텍스트 스위칭을해서 cpu 사용률을 높일 수 있음
- 이를 위해선 물리 메모리에 프레임을 할당해야 함 
- 물리 메모리의 크기는 한계가 있기 때문에 일부는 스왑 영역에 저장
- 멀티 프로그래밍 정도가 늘어나면 제한된 물리 메모리에 모든 프로세스를 올려야하고당장 실행되는 프레임을 제외한 나머지 프레임들은 스왑 영역에 저장되고 page fault가 많이 발생
- cpu가 작업하는 시간보다 스왑 작업에 많은 시간이 소요되고 cpu 사용률이 떨어짐
- 그럼 더 많은 프로세스를 메모리에 올리게되고 이렇게 반복하다보면 더 떨어짐
- 이를 쓰레싱이라고 부름
- 근본적인 원인은 메모리의 크기가 작아서 !

- 운영체제가 쓰레싱을 소프트웨어적으로 해결할 수 있는 방법
- 한 프로세스가 실행될 때 너무 많은 페이지를 할당하면 다른 프로세스가 사용할 페이지가 줄어들기 때문에 효율이 떨어짐
- 반면 너무 적은 페이지를 할당하면 page fault가 빈번, 스왑 요청이 많아 쓰레싱 발생 
- 이를 해결하기 위해 프로세스가 실행되면 일정량의 페이지를 할당하고 만약 page fault가 발생하면 더 많은 페이지를 할당
- 반면 page fault가 너무 적게 발생하면 페이지를 과하게 할당해 메모리가 낭비되는 것이라고 판단하고 페이지 회수
- 어떤 페이지 수를 유지할 지는 지역성 이론을 따름
- 현재 메모리에 올라온 페이지는 다시 사용할 확률이 높기 때문에 하나의 세트로 묶어서 메모리에 올림 -> 이를 워킹셋이라고 부름
- 워킹셋
	- 프로세스가 준비 상태에서 실행 상태가 되는 컨텍스트 스위칭을 할 때 사용 됨

## 주변장치 (I/O 디바이스, 저장장치)
- 그래픽카드, 하드디스크, SSD, 키보드, 마우스 등
- 주변장치들은 메인보드에 있는 버스로 연결됨
- 하나의 버스는 어드레스 버스, 데이터 버스, 컨트롤 버스로 이뤄짐
- I/O 디바이스는 이 3가지 버스를 따로 받을 수 있음
- 각 하드웨어에 맞게 외부 인터페이스도 존재
- 장치의 상태와 데이터를 보관할 수 있는 레지스터들도 존재
- 레지스터들은 입출력 작업을 할 때 데이터를 저장하는 역할, 이 값들은 CPU가 사용하기 위해 메모리로 이동되기도 함

- 주변장치는 데이터의 전송단위에 따라 캐릭터 디바이스/ 블록 디바이스 두 개로 나눌 수 있음
- 캐릭터 디바이스
	- 마우스, 키보드, 사운드 카드, 직렬 병렬 포트 등
	- 데이터 전송 단위가 캐릭터(글자)로 상대적으로 크기가 작음
- 블록 디바이스
	- 하드디스크, SSD, 그래픽카드 등
	- 데이터 전송 단위가 블록(범위)로 상대적으로 크기가 큼
- 여러 주변 장치는 메인 메모리 내의 버스로 연결되는데 예전에는 주변 장치들을 하나의 버스로 연결해서 사용
- CPU가 작업을 하다가 I/O 요청을 만나면 직접 입출력 장치에서 데이터를 가져왔는데 입출력 중에는 다른 작업을 하지 못했기 때문에 cpu 사용률이 떨어졌음
- 이를 해결하기 위해 입출력 제어기와 여러 개의 버스 추가

- cpu는 I/O 명령을 만나면 입출력 제어기에게 입출력 작업을 맡기고 다른 작업 실행
- 입출력 제어기에는 두 개의 채널인 시스템 버스와 입출력 버스와 구분
- 시스템 버스는 고속으로 작동하는 cpu와 메모리가 사용
- 입출력 제어기는 주변 장치가 사용
- 입출력 제어기는 세부적으로 느린 장치와 빠른 장치를 구분하기 위해 다시 고속 입출력버스와 저속 입출력 버스의 두 개의 채널로 나뉨 -> 속도차이로 인한 병목 현상 해결
- 그래픽 카드는 예외적으로 매우 대용량의 데이터를 다루기 때문에 시스템 버스에 바로 연결해 사용
- 입출력 제어기는 여러 주변 장치를 처리하는데 입출력 버스에서 온 데이터를 메모리로 옮김
- 메모리는 cpu의 명령으로 움직이기 때문에 입출력 제어기가 메모리에 접근하기 위해선 cpu가 필요
- 이 때 cpu없이도 입출력 제어기가 메모리의 접근하게 할 수 있도록 DMA 추가
- DMA는 직접 메모리 접근이라는 의미
- cpu와 dma가 사용하는 메모리가 겹치지 않도록 각 메모리 영역이 나뉘는데 이를 memory mapped I/O라고 함

## 마우스 키보드(캐릭터 디바이스)
- 주변장치
- 광학 마우스
	- 마우스 아래에 달린 카메라가 표면으로 초당 1500회가 넘는 사진을 찍어 마우스의 디바이스 컨트롤러 내 DSP로 보냄
	- DSP는 이 사진을 분석해 마우스의 x축 좌표와 y축 좌표 움직임을 캐치함
	- DSP가 마우스의 움직임과 클릭같은 데이터를 감지하면 디바이스 컨트롤러는 cpu에게 인터럽트를 보내고 마우스 드라이버가 동작해서 데이터를 읽어감
	- 마우스 드라이버는 운영체제에게 이벤트 신호를 주는데 운영체제는 이 이벤트를 포그라운드 애플리케이션으로 전달해주고 해당 애플리케이션은 받은 마우스 이벤트를 처리함
- 키보드
	- 사용자가 키보드를 누르면 키보드 디바이스 컨트롤러가 어떤 키를 입력받았는지 알아냄
	- cpu에게 인터럽트를 보내고, 키보드 드라이버는 운영체제에게 이벤트를 보냄
	- 운영체제는 포그라운드 애플리케이션으로 이벤트를 전달해주고 애플리케이션엣 해당 키에 맞는 동작 수행

## 하드디스크/ flash memory(SSD) (블록 디바이스)
- 하드디스크의 구조
	- 스핀들이라는 막대
	- 스핀들에는 플래터라는 원판들이 붙어 있음
	- 플래터는 자기화된 원판으로 이뤄져있는데 디스크 암이 읽어쓰기 헤드로 플래터의 표면을 읽음
	- 플래터는 여러 개의 트랙으로 구성되어 있고 표면에 자성이 있기 때문에 표면이 n극을 띠면 0, s극을 띠면 1로 인식
	- 보통 하드디스크의 플래터 수는 두 개 이상
	- 헤드는 디스크 암에 고정되어 있기 때문에 모든 헤드는 항상 같이 움직임
	- 헤드가 움직이면 이 헤드들은 여러 개의 플래터를 가리키게 되는데 이때 여러 개의 플래터에 있는 같은 트랙의 집합을 실린더라고 부름
	- 트랙은 다시 여러개의 섹터로 나뉘는데 이 섹터는 하드디스크의 가장 작은 단위
- 하드디스크에서 데이터를 읽어오는 예시
	- 유저 프로세스가 하드디스크의 특정 섹터에 접근하고 싶어 실린더 c로 가서 트랙 b에 있는 섹터 d를 읽어라 라는 명령을 보냄
	- 디스크 암이 헤드를 실린더 c로 이동시킴 -> seek, 헤드를 실린더로 이동시키는데 걸리는 시간을 seek time(하드디스크가 느린 이유)
	- 트랙 b의 섹터 d가 헤드에 닿을 때까지 스핀들을 회전시킴
	- 헤드의 섹터 d가 읽히면 작업이 끝남

- Flash memory(SSD)
	- 요즘은 SSD를 하드디스크보다 더 많이 사용
	- 데스크톱에는 플래시 메모리의 이점으로 많은 사람이 SSD를 사용하고 핸드폰이나 태블릿 같은 경우는 하드디스크를 넣을 큰 공간이 없어서 당연히 플래스 메모리를 사용
	- 하드디스크는 기계적으로 헤드를 움직여 속도가 많이 느리고 소음도 낮지만 플래시 메모리는 전기적으로 읽기 때문에 빠르고 조용
	- 자기적으로 처리하는 하드디스크는 자석을 갖다 대면 데이터가 손상되지만 플래시 메모리는 괜찮음
	- 하드디스크는 스핀들처럼 회전축같은것들이 있어서 충격에 매우 약하지만 플래시 메모리는 그렇지 않음
	- 단점은 특정한 지점에 데이터를 썼다면 덮어쓰기가 불가능하다는 것
	- 플래시 메모리는 지우기 가능한 횟수가 정해져 있음

## 파일과 파일 시스템
- 파일들은 하드디스크나 SSD와 같은 저장장치에 저장됨
- 메모리와 마찬가지로 사용자가 직접 저장하게 되면 중요한 정보가 훼손될 가능성이 있기 때문에 사용자가 운영체제를 통해 요청하면 운영체제가 안전하게 저장해줌
- 운영체제는 파일을 관리하기 위해 파일관리자를 뒀는데 이를 파일 시스템
- 파일 관리자는 가상 메모리에서 메모리 관리자가 페이지 테이블을 이용해서 가상 주소를 물리 주소로 변환하는 것처럼 파일 테이블을 이용해서 파일 관리

- 파일시스템의 기능
	- 파일과 디렉토리 생성
	- 파일과 디렉토리 수정, 삭제
	- 파일 권한 관리: 요즘 운영체제는 다중 사용자 기능을 지원하기 때문에 보호 목적
	- 무결성 보장: 파일의 내용이 손상되지 않게 하기 위한 목적
	- 백업과 복구: 예기치 못한 사고로부터 백업과 복구
	- 암호화: 파일을 암호화해 파일 보호
- 파일 시스템은 하드디스크나 플래시 메모리같은 저장 장치에 저장되기 때문에 전송 단위가 블록
- 저장 장치의 전송 단위는 블록이지만 사용자는 바이트 단위로 파일에 접근이 가능해야 하기에 이를 파일관리자가 중간에서 관리
- 유닉스 운영체제는 파일에 확장자가 없지만 윈도우의 경우 파일마다 확장자 
- 확장자로 파일의 속성을 알 수 있음
	- .exe는 실행 파일: 운영체제가 바로 프로세스를 만들어 실행
	- .jpg, .bmp, .png는 이미지 파일: 포토샵이나 그림판 실행
	- .mp3, .wav는 음악 파일: 곰플레이어나 아이튠즈 실행
	- .mp4, .avi는 동영상 파일
- 파일은 헤더와 데이터로 이뤄져 있는데 헤더에는 파일의 속성들이 담겨 있음
- 운영체제는 파일을 관리하기 위해 정보를 보관하는 파일 디스크립터라는 파일 제어 블록을 가지고 있음
- 파일 디스크립터는 파일마다 독립적으로 존재하고 저장장치에 존재하다가 파일이 오픈되면 메모리로 이동
- 파일 디스크립터는 파일 시스템이 관리하고 사용자는 직접 참조할 수 없음
- 사용자는 파일 시스템이 건내준 파일 디스크립터로 파일에 접근할 수 있음

- c언어로 예시
	- 사용자는 파일에 접근하기 위해 open, close라는 시스템 콜을 이용
	- 사용자가 open 함수를 이용해 test.txt라는 파일을 읽기용으로 열기 요청을 하면 운영체제는 해당 파일을 찾아 파일 디스크립터를 전달해줌
	- 사용자가 close함수를 이용해 파일 닫기 요청을 하면 운영체제는 해당 파일 디스크립터를 참조해 파일을 닫아줌
- 파일은 데이터의 집합으로 볼 수 있는데 이 데이터의 집합을 어떻게 구성하느냐에 따라 종류를 나눌 수 있음
	- 순차 파일 구조: 파일의 내용이 연속적으로 이어진 형태(카세트 테이프)
		- 모든 데이터가 순서대로 기록되기 때문에 공간에 낭비가 없고 구조가 단순
		- 특정 지점에 바로 이동이 어려워 데이터를 삽입하거나 삭제하려면 탐색하는데 시간이 많이 걸린다는 것
	- 직접 파일 구조: 저장하려는 데이터를 해시함수를 통해 저장위치를 결정하는 파일 구조
		- 이 구조는 자료구조에서 해시테이블이라고 불리는 방식
		- 요즘 많이 사용되는 데이터 포맷인 json도 이 방식
		- 해시함수를 이용하기 때문에 데이터 접근이 굉장히 빠름
		- 해시함수의 선정이 굉장히 중요해서 해시함수를 잘 골라야 함
		- 저장공간이 낭비될 수 있음
	- 인덱스 파일 구조: 순차 접근과 직접 접근 방식의 장점을 취한 것
		- 예를 들면 음악 재생 프로그램에서 재생 목록
		- 재생목록은 모두 순차 데이터로 저장되어 있음
		- 재생을 누르면 순차적으로 재생하는데 특정 데이터를 재생하고 싶다고 하면 인덱스 테이블에 접근해 블록 번호를 알아냄
		- 순차 데이터의 해당 블록 번호로 이동해 그 데이터 재생

## 디렉토리 
- 파일을 하나의 공간에 보관하면 파일이 많아지면서 복잡
- 관련있는 파일을 모아둘 수 있도록 디렉토리 등장
- 디렉토리는 한 개 이상의 파일을 가질 수 있고 자식 디렉토리도 가질 수 있음
- 디렉토리는 여러 층으로 구성되는데 최상위 층의 디렉토리를 루트 디렉토리라고 함
- 유닉스와 리눅스의 경우 루트디렉토리를 슬래시(/)로 표현하고 디렉토리와 디렉토리의 구분을 위해서도 슬래시(/)사용
- 윈도우의 경우 루트 디렉토리는 파티션 이름으로 사용하는데 보통 C:로 표시
- 윈도우는 디렉토리와 디렉토리의 구분을 역슬래시( \ )로 함
- 디렉토리도 파일이지만 일반 파일에는 데이터가, 디렉토리에는 파일 정보가 저장

- 디렉토리 헤더는 디렉토리 정보가 시작되는 위치를 가리킴
- 디렉토리에 점 한 개와 점 두개가 있는데 이는 현재 디렉토리와 상위 디렉토리를 나타냄
- 루트 디렉토리의 경우 상위 디렉토리가 없기 때문에 점 두개도 자기 자신을 가리킴

- 디렉토리 구조
	- 다단계 디렉토리 구조
	- 어떠한 디렉토리에서도 하위 디렉토리를 만들 수 있는 트리 구조
	- 우리가 쓰는 운영체제는 트리 구조에서 순환이 생기는데 그 이유는 바로가기 기능 때문
	- windows는 바로가기 아이콘을 만들어 특정 디렉토리에서 다른 디렉토리로 바로 이동하는 기능이 있기 때문에 순환이 있는 트리 구조

## 파일과 디스크
- 파일시스템은 메모리와 비슷
- 페이징과 같이 전체 디스크 공간을 일정한 크기로 나누고 그 공간에 주소를 할당해 관리
- 일정한 크기로 나눈 공간을 메모리에선 페이지라고 부르고 파일 시스템에서는 블록이라고 부름
- 한 블록의 크기는 1부터 8kb정도
- 파일 시스템은 파일 정보를 파일 테이블로 관리하는데 여가엔 파일이 시작하는 블록의 위치 정보도 담겨 있음
- 하나의 파일은 여러 개의 블록으로 이뤄져있는데 이 블록들을 어떻게 연결하는지에 따라 연속할당과 불연속할당으로 나눔
	- 연속 할당: 파일을 구성하는 블록들을 디스크에 연속적으로 저장
		- 파일의 시작 블록만 알면 파일 전체를 찾을 수 있음
		- 메모리에서 세그멘테이션처럼 외부단편화 발생하기 때문에 실제로 사용 x
	- 불연속 할당: 디스크의 비어있는 공간에 데이터를 분산해 저장하는 방식
		- 분산된 블록은 파일 시스템이 관리
		- 불연속 할당으로는 연결 할당과 인덱스 할당
- 불연속할당 - 연결 할당
	- 자료 구조에는 연결 리스트 -> 파일에 속한 데이터를 연결 리스트로 관리
	- 연결 리스트는 각 노드가 데이터와 포인터를 가짐
	- 데이터는 말 그대로 해당 노드가 저장하고 있는 데이터이고 포인터는 이전 노드와 다음 노드의 주소를 가리킴
	- 하나의 노드의 포인터를 이용해 다른 노드로 이동하여 모든 노드를 순환 가능
	- 파일 테이블에는 시작 블록에 대한 정보만 저장하고 나머지는 연결 리스트를 이용해 다른 블록에 접근
	- 파일 c를 참조한다고 하면 파일 테이블을 참조해 첫 번째 블록에 있는 걸 알아냄
	- 파일 할당 테이블의 첫 번째 행에 있는 블록으로 접근
	- 1번블록에 있는 데이터를 가져오고 1번이 가리키고 있는 3번 블록을 다시 참조해서 데이터를 가져옴
	- 이런식으로 null 값을 만날 때까지 데이터를 참조하면 모든 데이터를 얻을 수 있음
- 불연속할당 - 인덱스 할당
	- 인덱스 할당 방식은 테이블의 블록 포인터가 데이터 블록에 집적 연결하는 것이 아니라 데이터들의 인덱스를 가지고 있는 인덱스 블록을 연결
	- 인덱스 할당은 데이터가 많아서 테이블이 꽉 찬 경우 인덱스 블록을 더 만들어 연결하기 때문에 테이블을 확장할 수 있음
	- 파일 크기가 작다면 데이터를 바로 참조하는 블록 포인터를 이용하고 파일 크기가 간접 포인터를 이용해 많은 데이터에 접근할 수 있음
	- 더 큰 데이터가 필요하다면 2중 3중 간접 포인터 사용 -> i node라는 이름으로 유닉스와 리눅스에서 많이 사용되고 있음
	- 디스크는 일정한 크기의 블록으로 나뉘고 블록의 크기는 1부터 8kb정도
	- 디스크를 1kb정도로 나누면 낭비되는 공간을 줄일 수 있지만 관리해야 될 블록의 수도 많아짐
	- 반대로 8kb로 나누면 관리해야 할 블록의 수는 적지만 내부 단편화로 낭비되는 공간이 많아짐
	- 파일 시스템은 효율적인 관리를 위해 빈 공간을 모아둔 free block list를 가지고 있음
	- 특정 파일을 삭제한다면 파일 시스템은 파일의 모든 정보를 지우는 것이 아니라 파일 테이블의 헤더를 삭제하고 free block list에 추가 
	- 이렇게 처리하면 사용자는 파일이 삭제된 것 처럼 느껴지는데 사용했던 블록의 데이터는 그대로 남아있기 때문에 포렌식 가능

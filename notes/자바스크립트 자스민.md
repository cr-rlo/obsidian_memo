- 자스민은 자바스크립트 코드를 테스트하기 위한 오픈 소스 테스팅 프레임워크
- 자바스크립트 코드가 의도한 대로 정확히 작동하는지 확인하기 위해 사용하는 검사 도구
## 프레임워크
- 미리 만들어진 뼈대
- 일반코딩: 주도권이 '나에게'
- 프레임워크 이용: 이미 뼈대가 갖춰져 있는 것에 내가 그 이후 작업. 정해진 규칙을 따라야 하지만 훨씬 빠르고 견고한 작업 가능

## 자스민의 주요 특징
- 행동 주도 개발 지향 BDD
	- "어떤 기능이 어떻게 동작해야 한다"는 시나리오를 작성하듯 테스트 코드를 짤 수 있음
	- 덕분에 개발자뿐만 아니라 비개발자가 읽어도 이해하기 쉬운 문장 구조를 가짐
- 독립성
	- 다른 자바스크립트 프레임워크(jQuery, Angular)등에 의존하지 않고 단독으로 실행 가능함
- 클린 문법
	- 코드가 매우 직관적
## 코드 구조 (간단한 예시)
- 자스민 테스트는 기본적으로 describe, it, expect 세가지 키워드를 중심으로 구성됨
- describe
	- 테스트 묶음 (무엇을 테스트할 것인가?)
	- describe("더하기 함수 테스트", function( ){ 
- it
	- 개별 테스트 케이스 (어떤 결과가 나와야 하는가?)
	- it( "1더하기 2는 3이어야 한다.", function( ){ } )
- expect
	- 결과 확인( 기댓값과 실제값 비교 )
	- expect( 1+2 ).toBe( 3 ); } );
## 자스민을 쓰는 이유
- 버그 예방
	- 코드를 수정했을 때 다른 부분이 망가지지 않았는지 즉시 확인할 수 있음
- 문서화 역할
	- 테스트 코드 자체가 해당 기능이 어떻게 작동해야 하는지 보여주는 설명서 역할을 함
- 자동화
	- 매번 수동으로 코드를 실행해 볼 필요 없이, 버튼 하나로 수백 개의 테스트를 순식간에 끝낼 수 있음
## 자스민의 3단 구조 자세히 분석
- <mark style="background: #FFB86CA6;">describe</mark> 
	- 가장 큰 범주 (테스트 꾸러미)
	- 지금부터 무엇을 테스트 할 것인지 주제를 정의함 
	- 문법: describe("주제명", function() { ... });
	- 역할: 관련된 여러 개의 테스트( it )을 하나로 묶어주는 그룹화 역할
- <mark style="background: #FFB86CA6;">it</mark>
	- 실제 테스트가 이뤄지는 최소 단위 (개별 테스트 케이스)
	- 문법: it("기대하는 동작 설명", function() { ... });
	- 역할: 구체적으로 어떤 상황에서 어떤 결과가 나와야 하는지 명시. 하나의 describe 안에 여러 개의 it이 들어갈 수 있음
- <mark style="background: #FFB86CA6;">expect와 Matchers</mark>
	- 얻은 결과와 예상한 값이 일치하는지 확인 (실제 검증)
	- 문법: expect(실제결과값).toBe(예상값);
	- Matchers: .toBe( )와 같은 함수를 Matcher라고 부름
		- .toBe(true) : 정확히 일치하는지 ( === )
		- .toEqual( { name: 'AI' } ): 객체 내부 내용이 같은지
		- .toContain( "apple" ): 배열에 특정 값이 들어있는지
		- .toBeLessThan( 10 ): 10 보다 작은지
## 자스민 작동 프로세스(Life Cycle)
- 테스트를 할 때 매번 반복되는 작업이 있을 수 있음
- 이를 위해서 전처리/ 후처리 함수를 제공
- beforeEach( ): 각 it 테스트가 실행되기 직전에 매번 실행됨(테스트 환경 초기화)
- afterEach( ): 각 it 테스트가 끝난 직후에 매번 실행됨(정리 작업)
- beforeAll( ) / afterAll( ): 전체 테스트 세트 시작 전/후에 딱 한 번만 실행됨
## 자스민 파일 나누기
- view.js
	- 실제 기능 코드
	- 사용자에게 보여지는 화면을 제어하거나 실제 기능을 수행하는 진짜 자바스크립트 코드
	- 웹사이트가 실제로 돌아갈 때 작동하는 주인공
	- 웹 사이트 방문자들이 사용
- spec.js
	- 테스트 코드
	- view.js가 제대로 만들어졌는지 검사하는 시험지
	- 서비스 배포 시에는 필요없지만 개발하는 동안 버그를 잡기 위해 꼭 필요함
	- 자스민의 문법은 다 여기서 쓰임
	- 개발자가 사용
- 작동원리
	- 자스민을 실행하면 자스민이 두 파일을 동시에 읽음
	- 먼저 view.js에 있는 함수들을 메모리에 올려둠
	- 그다음 spec.js를 읽으면서 메모리에 있는 함수들을 실행해서 결과가 예상한대로 나오는지 확인하는 테스트를 진행함
## 자스민 spyOn
- 실제 함수를 실행하지 않고도, 그 함수가 호출되었는지, 어떤 값을 들고 갔는지 몰래 감시하는 도구
- spyOn이 필요한 이유
	- 결제 버튼을 테스트 한다고 가정해보자
	- 이 때 테스트 할 때마다 실제로 돈이 결제되면 큰 일
	- 진짜 결제 함수 위에 자스민 스파이 함수
	- 진짜 결제는 일어나지 않게 막으면서, 함수가 호출되었는지 확인할 수 있음
- spyOn의 기본 문법
	- spyOn(대상객체, "함수이름")
	- spyOn(market, "buyItem");
	- 이렇게 호출하면 market.buyItem 함수는 자스민의 감시
- 스파이가 할 수 있는 일들 (자주 쓰는 기능)
	- 호출 여부 확인
		- toHaveBeenCalled
			- 호출 여부 확인
			- 함수가 한 번이라도 실행되었는지 확인
		- it("버튼을 누르면 buyItem 함수가 실행되어야 한다", function() { spyOn(market, "buyItem"); 
		- clickButton();  // 버튼 클릭 시뮬레이션
		- expect(market.buyItem).toHaveBeenCalled(); // "실행 됐지?"라고 확인 });
	- 전달된 값 확인
		- toHaveBeenCalledWith
			- 함수가 실행될 때 어떤 데이터를 가지고 갔는지 확인
		- t("사과를 살 때는 'apple'이라는 글자가 전달되어야 한다", function() { spyOn(market, "buyItem"); 
		- buyApple(); 
		- expect(market.buyItem).toHaveBeenCalledWith("apple"); // "사과 사러 간 거 맞아?" });
	- 가짜 결과값 돌려주기
		- and.returnValue
			- 진짜 함수를 실행하는 대신, 내가 원하는 값을 억지로 뱉게 만듦
			- 네트워크 통신 등을 흉내 낼 때 활용
		- it("서버가 점검 중일 때 에러 메시지가 나오는지 확인", function() { // 원래는 서버에 물어봐야 하지만, 스파이가 대신 "점검중"이라고 대답하게 함 
		- spyOn(server, "checkStatus").and.returnValue("OFFLINE");
		- const status = server.checkStatus(); 
		- expect(status).toBe("OFFLINE"); });
- spyOn VS createSpy
	- spyOn(obj, 'method'): 이미 존재하는 객체의 함수에 스파이를 붙일 때 씀 (가장 많이 씀)
	- jasmine.createSpy('name'): 존재하지 않는 새로운 가짜 함수를 아예 새로 만들 때 사용. 보통 콜백 함수(함수 안에 인자로 들어가는 함수)를 테스트할 때 유용
## 의존성 주입
- 의존성
	- 코드에서 A라는 클래스나 함수가 동작하기 위해 B가 필요하다면 A는 B에 의존한다고 함
- 의존성 주입을 하는 이유(모듈 개발 관점)
	- 의존성 주입을 쓰면 코드의 유연성이 크게 좋아짐
	- 문제상황: 만약 내가 코드 안에 `new SamsungTV()`라고 직접 박아 넣으면(Hard Coding), 나중에 LG TV로 바꾸고 싶을 때 코드 전체를 다 뜯어고쳐야 함
	- 해결 방법: 나는 그냥 "TV가 필요해"라고만 선언. 그리고 밖에서 Samsung을 줄지, LG를 줄지 결정. 이렇게 하면 부품 갈아 끼우기가 아주 쉬워짐
- 테스트(자스민)등에서 DI가 필수인 이유
	- 테스트를 쉽게하기 위해서 
	- 외부 서버와 상관없이 테스트가 가능하게 만들어줌
